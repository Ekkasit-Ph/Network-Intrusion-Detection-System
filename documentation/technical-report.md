# รายงานเชิงลึกทางเทคนิค — ระบบตรวจจับการบุกรุกเครือข่ายด้วย Denoising Autoencoder + SHAP

เอกสารนี้อธิบายรายละเอียดเชิงลึกของการออกแบบและการตัดสินใจเชิงวิศวกรรมในแต่ละโมดูล
เพื่อนำไปเรียบเรียงลงรายงาน/เล่มวิทยานิพนธ์ ทุกตัวเลขและการอ้างอิงมาจากโค้ดและการทดลองจริง

สารบัญ
1. ภาพรวมสถาปัตยกรรม
2. การสกัดฟีเจอร์: จาก nfstream สู่สคีมา NF-ToN-IoT-v2 (43 ฟิลด์)
3. ฟีเจอร์ที่ nfstream ไม่มีให้ — การเขียน NFPlugin สกัดเอง
4. การสร้างฟีเจอร์เชิงพฤติกรรม (behavioral feature engineering)
5. ฟีเจอร์ใดส่งผลต่อการตรวจจับการโจมตีแต่ละประเภท
6. ประเด็นเชิงลึกของชุดข้อมูลและการวัดผล
7. การค้นพบ domain shift และการฝึกซ้ำต่อเครือข่าย
8. ความสามารถในการอธิบายด้วย SHAP

## 1. ภาพรวมสถาปัตยกรรม

ระบบประกอบด้วย 6 โมดูลที่ทำงานต่อเนื่องกันเป็นสายท่อ (pipeline)

| โมดูล | หน้าที่ | เทคโนโลยีหลัก |
|---|---|---|
| 1. Flow extraction | สกัดแพ็กเก็ตดิบเป็นระเบียนโฟลว์ (flow record) 43 ฟิลด์ | nfstream + nDPI + NFPlugin ที่เขียนเอง |
| 2. Preprocessing | ทำความสะอาด, เข้ารหัส categorical, log-transform, สร้างฟีเจอร์พฤติกรรม, สเกล | pandas, scikit-learn |
| 3. Model inference | คำนวณ reconstruction error เทียบกับ threshold | Denoising Autoencoder (PyTorch) |
| 4. Explanation | อธิบายว่าฟีเจอร์ใดทำให้ error สูง | Kernel SHAP |
| 5. Dashboard | แสดงผลสด + incident + firewall gaps | FastAPI + หน้าเว็บ static |
| 6. Firewall verification | เทียบผลตรวจจับกับนโยบายไฟร์วอลล์ → รายงานช่องโหว่ | เปรียบเทียบกฎ OpenFlow/iptables |

**หลักการสำคัญของโมเดล** เป็น *unsupervised anomaly detection* — ฝึกด้วยทราฟฟิกปกติ (benign) เท่านั้น
โมเดล autoencoder เรียนที่จะ "สร้างใหม่ (reconstruct)" เวกเตอร์ฟีเจอร์ของทราฟฟิกปกติให้ได้ใกล้เคียง
ทราฟฟิกที่ผิดปกติจะสร้างใหม่ได้แย่ → ค่า reconstruction error สูง → เกินเกณฑ์ = ผิดปกติ
ข้อดีคือไม่ต้องมีตัวอย่างการโจมตีตอนฝึก และจับการโจมตีแบบใหม่ที่ไม่เคยเห็นได้

## 2. การสกัดฟีเจอร์: จาก nfstream สู่สคีมา NF-ToN-IoT-v2 (43 ฟิลด์)

ชุดข้อมูลฝึก **NF-ToN-IoT-v2** ถูกสร้างด้วยเครื่องมือเชิงพาณิชย์ **nProbe** ซึ่งส่งออกระเบียนโฟลว์
43 ฟิลด์ตามรูปแบบ NetFlow เมื่อนำระบบไปใช้จริง เราไม่มี nProbe จึงใช้ไลบรารีโอเพนซอร์ส **nfstream**
(ซึ่งใช้ **nDPI** engine เดียวกับ nProbe) แต่ nfstream **ไม่ได้ให้ฟิลด์ครบตามสคีมา** จึงต้องเขียน
ชั้นแปลง (mapping layer) ใน `source/extraction/sensor.py` เพื่อให้เวกเตอร์ฟีเจอร์ตรงกับที่โมเดลคาดหวัง
**เป๊ะทุกตำแหน่ง** (ถ้าคอลัมน์สลับตำแหน่งแม้ตัวเดียว โมเดลจะเห็นฟีเจอร์ผิดช่อง → ผลเพี้ยนทั้งหมด)

### 2.1 ฟิลด์ที่ได้จาก nfstream โดยตรง
nfstream ให้สถิติระดับโฟลว์แบบสองทิศทาง (bidirectional) มาแล้ว เช่น
- ที่อยู่/พอร์ต/โปรโตคอล: `src_ip`, `dst_ip`, `src_port`, `dst_port`, `protocol`
- ปริมาณ: `src2dst_bytes/packets` → `IN_BYTES/IN_PKTS`, `dst2src_bytes/packets` → `OUT_BYTES/OUT_PKTS`
- ระยะเวลา: `bidirectional_duration_ms` → `FLOW_DURATION_MILLISECONDS`
- ขนาดแพ็กเก็ตสุดขั้ว: `bidirectional_max_ps` → `LONGEST_FLOW_PKT`, `bidirectional_min_ps` → `SHORTEST_FLOW_PKT`
- TCP flags: นับจาก `bidirectional_syn/ack/fin/rst/psh/urg/ece/cwr_packets` แล้วประกอบเป็นไบต์เดียว (`TCP_FLAGS`, `CLIENT_TCP_FLAGS`, `SERVER_TCP_FLAGS`)

### 2.2 รายละเอียดที่ต้องจัดการให้ตรงกับ nProbe (train/serve skew)
ความต่างเล็ก ๆ ระหว่าง nfstream กับ nProbe ทำให้ค่าฟีเจอร์เพี้ยนและโมเดลผิดพลาด หากไม่แก้:

**(ก) `accounting_mode` — ชั้นเลเยอร์ที่นับไบต์** nfstream ค่าเริ่มต้น (mode 0) นับทั้งเฟรม Ethernet
ส่วน nProbe เขียนชุดข้อมูลที่ชั้น IP หลักฐานยืนยันในข้อมูลเอง: `SHORTEST_FLOW_PKT` ต่ำสุดอยู่ที่ **40**
(ส่วนหัว TCP เปล่า ๆ) ไม่ใช่ 54/60 (ซึ่งเป็นค่าที่กรอบ Ethernet จะกำหนด) → ต้องตั้ง
`accounting_mode = 1` (ชั้น IP) มิฉะนั้น `IN_BYTES/OUT_BYTES` และคอลัมน์ความยาวแพ็กเก็ตทั้งสี่จะ
พองเกิน 14 ไบต์ต่อแพ็กเก็ต และความผิดพลาดนี้ลามไปถึง `*_SECOND_BYTES` และ `*_AVG_THROUGHPUT` ด้วย

**(ข) `MIN_IP_PKT_LEN` — ค่าที่ขึ้นกับทิศทาง** nProbe รายงานค่านี้เป็น 0 บนโฟลว์ทางเดียว (one-directional)
ตรวจสอบกับข้อมูลฝึก 3 ล้านแถว: ทั้งสองคอลัมน์เท่ากันเสมอเมื่อ `OUT_PKTS > 0`, และเป็น 0 ทั้งหมด
สำหรับ 2,278,969 แถวที่ `OUT_PKTS == 0` (ยกเว้นแถวเดียว) และ **76% ของแถวฝึกถือค่า 0 นี้**
จึงต้อง emit `MIN_IP_PKT_LEN = bidirectional_min_ps เฉพาะเมื่อมี dst2src_packets, มิฉะนั้น 0`
ไม่เช่นนั้นจะไม่ตรงกับความเข้าใจของโมเดลบนทราฟฟิกส่วนใหญ่

**(ค) `L7_PROTO` — การเข้ารหัสโปรโตคอลชั้น 7** nfstream รายงานโปรโตคอลเป็น *ชื่อ* ("HTTP", "DNS")
แต่สคีมาฝึกเก็บเป็น *เลข* ตามการเข้ารหัส `master.app` ของ nProbe จึงมีโมดูล `l7_proto.py` สร้าง
mapping ชื่อ→เลข กลับคืนมาจากไลบรารี nDPI ที่โหลดอยู่

### 2.3 การตั้งค่า CPU affinity (บั๊กที่วัดได้)
nfstream (ผ่าน libpcap/nDPI) **หด CPU affinity ของโปรเซสจาก 8 คอร์เหลือ 2 แบบถาวร** ส่งผลให้
throughput ของการให้คะแนนลดจาก 2.7M เหลือ ~10.7k โฟลว์/วินาที และ SHAP ช้าลงจาก 90 เป็น 9.4 ms
แก้โดยบันทึก affinity เดิมก่อนเรียก nfstream แล้วคืนค่าหลังสกัดแต่ละโฟลว์ (ดู `sensor.py` ฟังก์ชัน `_restore()`)

## 3. ฟีเจอร์ที่ nfstream ไม่มีให้ — การเขียน NFPlugin สกัดเอง

**นี่คือหัวใจของงานสกัดฟีเจอร์** ฟิลด์จำนวนมากในสคีมา NetFlow ต้องอ่าน*ไบต์ดิบของแต่ละแพ็กเก็ต*
ซึ่ง nfstream มาตรฐานไม่ทำให้ จึงเขียนปลั๊กอิน `NetFlowV2Fields(NFPlugin)` ใน
`source/extraction/nfplugin.py` ที่ hook เข้ากับทุกแพ็กเก็ตของโฟลว์ (callback `on_update`)
เพื่อแกะข้อมูลจากส่วนหัวและเพย์โหลดเองแล้วเก็บสะสมไว้ที่ `flow.udps.*`

ฟีเจอร์ที่ต้องสกัดเองพร้อมวิธี:

| ฟีเจอร์ | ต้องสกัดจาก | วิธี |
|---|---|---|
| `MIN_TTL`, `MAX_TTL` | ฟิลด์ TTL ในส่วนหัว IP ของทุกแพ็กเก็ต | อ่าน byte offset ของ TTL แล้วเก็บ min/max |
| `TCP_WIN_MAX_IN/OUT` | ฟิลด์ Window ในส่วนหัว TCP | `parse_tcp_window()` แล้วเก็บค่าสูงสุดแยกทิศทาง |
| `NUM_PKTS_*_BYTES` (5 ช่วง) | ความยาวแพ็กเก็ต | จัดแต่ละแพ็กเก็ตลงถัง (histogram) ตามขนาด |
| `RETRANSMITTED_IN/OUT_BYTES/PKTS` | เลขลำดับ TCP (sequence number) | เก็บเซ็ตของ (seq, payload_len) ที่เคยเห็นต่อทิศทาง หากซ้ำ = retransmission |
| `ICMP_TYPE`, `ICMP_IPV4_TYPE` | ส่วนหัว ICMP | `parse_icmp_type_code()` |
| `DNS_QUERY_ID`, `DNS_QUERY_TYPE`, `DNS_TTL_ANSWER` | เพย์โหลด DNS | **เขียน DNS parser เอง** (`parse_dns()`, `_skip_dns_name()` รองรับ name compression pointer 0xC0) |
| `FTP_COMMAND_RET_CODE` | เพย์โหลด FTP | `parse_ftp_return_code()` |

ประเด็นเชิงลึกที่ควรเขียนในรายงาน:
- **การตรวจ retransmission** ทำโดยจำคู่ `(sequence number, TCP payload length)` ที่เคยเห็นในแต่ละทิศทาง
  (`flow.udps._seen_seqs`) เมื่อเจอซ้ำจึงนับเป็นการส่งซ้ำ — nfstream ไม่มีตัวนับนี้
- **DNS over TCP** มี length prefix 2 ไบต์นำหน้า ต้องตัดออกก่อน parse (`strip_tcp_dns_length_prefix()`)
- ค่าเริ่มต้นเมื่อโปรโตคอลไม่เกี่ยวข้อง: ฟิลด์ ICMP/DNS/FTP ถูกตั้งเป็น 0 ใน `on_init()` ซึ่งตรงกับ
  ความหมาย "ไม่ใช่โปรโตคอลนี้" ในชุดข้อมูล (คอลัมน์เหล่านี้อยู่ใน `PROTOCOL_SPECIFIC_COLS`)

> สรุปประเด็นสำหรับรายงาน: การนำโมเดลที่ฝึกบนข้อมูล nProbe ไปใช้กับ nfstream ไม่ใช่แค่ "เรียก
> ไลบรารีแล้วได้ฟีเจอร์" แต่ต้อง **จำลองพฤติกรรมการวัดของ nProbe ซ้ำ** ทั้งชั้นเลเยอร์ที่นับไบต์,
> การเข้ารหัส L7, ความแปลกของฟิลด์ที่ขึ้นกับทิศทาง, และการเขียนตัวแกะโปรโตคอลระดับเพย์โหลดเอง
> มิฉะนั้นเกิด *train/serve skew* ที่ทำให้ค่าฟีเจอร์เพี้ยนและโมเดลตัดสินผิด

## 4. การสร้างฟีเจอร์เชิงพฤติกรรม (behavioral feature engineering)

### 4.1 ปัญหาที่ต้องแก้
การโจมตีแบบ **scanning** (สแกนพอร์ต) และ **DDoS/password-spray** มีลักษณะพิเศษคือ
*โฟลว์เดี่ยว ๆ หน้าตาเกือบเหมือนคอนเนคชันสั้นปกติ* ความเป็นการโจมตีอยู่ที่ **รูปแบบข้ามหลายโฟลว์**:
- scanning = ต้นทางเดียวติดต่อ *หลายปลายทาง/หลายพอร์ต* ในช่วงสั้น (fan-out)
- DDoS/spray = *หลายต้นทาง* พุ่งเข้าปลายทางเดียว (fan-in)

autoencoder ที่มองทีละโฟลว์ **ไม่มีทางเห็นรูปแบบนี้** เว้นแต่จะป้อนฟีเจอร์ที่สรุปพฤติกรรมข้ามโฟลว์ให้แล้ว

### 4.2 ฟีเจอร์ที่เพิ่ม (ใน `source/preprocessing/engineer_features.py`)
- `SRC_DISTINCT_DST_IPS_LAST_W` — ต้นทางนี้ติดต่อ IP ปลายทางที่ต่างกันกี่ตัวใน W โฟลว์ล่าสุด
- `SRC_DISTINCT_DST_PORTS_LAST_W` — ต้นทางนี้ติดต่อพอร์ตปลายทางที่ต่างกันกี่พอร์ตใน W โฟลว์ล่าสุด (จับ scan)
- `DST_DISTINCT_SRC_IPS_LAST_W` — ปลายทางนี้ถูกต้นทางต่างกันกี่ตัวติดต่อ (จับ fan-in/DDoS)

### 4.3 เหตุผลที่ต้องเป็น "หน้าต่างเลื่อนต่อต้นทาง" ไม่ใช่ค่าสะสมรวม
NF-ToN-IoT-v2 มีเพียง ~10 เครื่องในห้องทดลองที่สร้าง 94% ของ 16.9 ล้านแถว และ**เครื่องเดียวกัน
สร้างทั้งทราฟฟิกปกติและการโจมตีหลายชนิด** (เช่น 192.168.1.31: benign 2.29M + ddos 798K + scanning 651K)
→ ถ้าใช้ค่าสะสมรวมต่อ IP ("IP นี้เคยติดต่อกี่ปลายทางตลอดทั้งไฟล์") ค่าจะเกือบคงที่ต่อ IP และโมเดลจะ
**เรียนรู้ว่า "นี่คือเครื่องไหน" แทนที่จะเรียนรู้พฤติกรรมสแกนจริง** (testbed-specific shortcut) ซ้ำยัง
*รั่วข้อมูล* เพราะค่าฟีเจอร์ของแถว benign จะถูกแถวโจมตีของ IP เดียวกันที่ตกไปอยู่ชุด val/test มารบกวน

**หน้าต่างเลื่อน W=50 โฟลว์ต่อต้นทาง** แก้ปัญหานี้ — ค่าเปลี่ยนไปทีละแถวแม้เป็นเครื่องเดียวกัน
(ต่ำตอนทำงานปกติ พุ่งตอนเกิด scan burst) จึงพกสัญญาณพฤติกรรมจริง ไม่ใช่ตัวตนของเครื่อง
และยัง **ตรงกับสิ่งที่ deployment จริงจะทำได้** (ตัวนับแบบ rolling ต่อต้นทาง) → การคำนวณแบบ batch
(ตอนฝึก) กับ online (ตอนใช้งานจริง) เป็นฟีเจอร์เดียวกันเป๊ะ ไม่ใช่แค่คล้ายกัน

### 4.4 ข้อควรระวังเรื่องลำดับเชิงเวลา (causal ordering)
NF-ToN-IoT-v2 **ไม่มีคอลัมน์เวลาเริ่มโฟลว์เลย** (ตรวจสอบกับส่วนหัว CSV แล้ว) จึงใช้ *ลำดับแถวใน CSV เดิม*
เป็นตัวแทนเชิงเวลา (NetFlow exporter ต่อท้ายโฟลว์ที่จบแล้วตามลำดับเวลาคร่าว ๆ) และ **ต้องรัน
`add_behavioral_features` ก่อน `split_data`** (ซึ่งสับลำดับ) เพื่อให้ค่าทุกแถวคำนวณจากโฟลว์ก่อนหน้า
ของต้นทางเดียวกันเท่านั้น ไม่มีการรั่วข้ามชุด train/val/test ไม่ว่าแถวจะตกไปชุดใด

### 4.5 หลักฐานเชิงปริมาณ
การทดลองเพิ่มฟีเจอร์ทีละขั้น (ควบคุมตัวแปร) ได้ recall **29.59% → 45.87%** ที่ FPR เท่ากัน
> ข้อควรระวังในการนำเสนอ: ถ้าดู ablation แบบลบทีละฟีเจอร์ ฟีเจอร์ทั้งสามอยู่อันดับ 20/26/30 จาก 46
> เพราะ ablation ทีละตัว **ประเมินฟีเจอร์ที่สัมพันธ์กันต่ำกว่าความจริง** (เมื่อลบตัวหนึ่ง อีกสองตัวยัง
> ชดเชยได้) หลักฐานที่ควบคุมตัวแปรได้จริงคือการทดลอง *เพิ่ม* ทีละขั้นด้านบน

## 5. ฟีเจอร์ใดส่งผลต่อการตรวจจับการโจมตีแต่ละประเภท

### 5.1 ตัวแปรหลัก: เป็น TCP หรือ UDP
5 ฟีเจอร์เป็นของ TCP โดยเฉพาะ (`TCP_FLAGS`, `CLIENT_TCP_FLAGS`, `SERVER_TCP_FLAGS`,
`TCP_WIN_MAX_IN`, `TCP_WIN_MAX_OUT`) เมื่อเป็น UDP ค่าเหล่านี้เป็น 0 ทั้งหมด **100.00%** ไม่มีข้อยกเว้น
→ ไม่มีร่องรอย handshake ให้ดู เหลือเพียง "กี่ไบต์ กี่แพ็กเก็ต" จึงแยกยากขึ้น

| คลาส | recall บน TCP | recall บน UDP | recall รวม |
|---|---|---|---|
| password | 99.8% | 0.2% | 99.10% |
| ddos | ~100% | ~0% | 98.88% |
| injection | 94.9% | 5.1% | 92.55% |
| **dos** | 14.5% | **85.5%** | **80.81%** |
| **xss** | 49.0% | **51.0%** | **74.04%** |
| scanning | 99.8% | — | 87.17% |

### 5.2 การจับคู่ชนิดการโจมตี ↔ ฟีเจอร์ที่ตรวจจับได้
- **scanning** → `SRC_DISTINCT_DST_PORTS_LAST_W` (fan-out) เป็นหลัก: โฟลว์สแกนเดี่ยวดูเหมือน
  คอนเนคชันสั้น แต่หน้าต่างพฤติกรรมเผยว่า "ต้นทางนี้แตะ 30+ พอร์ตใน 50 โฟลว์ เทียบกับเครื่องปกติที่แตะ 2–3"
- **ddos** → รูปแบบ fan-in (`DST_DISTINCT_SRC_IPS_LAST_W`) + ฟีเจอร์ปริมาณพร้อมกัน **6+ ฟีเจอร์**
  ต่างจาก benign → error สูงถึง **3.42× threshold** (แยกออกชัด)
- **password (brute-force)** → คอนเนคชันสั้นซ้ำ ๆ จากต้นทางเดียว ไบต์ใกล้เคียงกันหมด + ล้มเหลวแบบเดียวกัน
- **injection** → วิ่งบน TCP/HTTP เป็นหลัก มีร่องรอย handshake ให้โมเดลดู → recall สูง
- **dos** → flow เล็กมาก (1 แพ็กเก็ตไป-กลับ 63–71 ไบต์ duration 0) **ต่างจาก benign แค่ 2 ฟีเจอร์**
  → error แค่ **1.35× threshold** (เบียดเส้น) ที่หลุดกับที่จับได้เป็นทราฟฟิกชนิดเดียวกัน error แค่ตก
  คนละฝั่งของเกณฑ์

### 5.3 สองกรณีที่ต้องแยกอธิบาย (ไม่ใช่ทุกจุดอ่อนคือจุดอ่อนของโมเดล)

**xss (74.04%) = label noise ของชุดข้อมูล ไม่ใช่จุดอ่อนของโมเดล**
- เฉพาะ flow TCP ตรวจจับได้ **99.35% สูงที่สุดในทุกคลาส**
- flow UDP ในคลาสนี้มี `L7_PROTO = Unknown` **100.0%** เหมือน benign UDP ทุกประการ
- XSS วิ่งบน HTTP ซึ่งต้อง TCP เสมอ → flow UDP 65 ไบต์ **เป็น XSS ไม่ได้ในทางเทคนิค** (ติด label
  มาเพราะเกิดในเซสชันเดียวกันตอนเก็บข้อมูล) การกระจาย error แยกเป็นสองกลุ่มขาดจากกัน
  (ที่หลุด p95 = 0.00102, ที่จับได้ p5 = 0.00275) = คนละประชากร

**dos (80.81%) = จุดอ่อนจริง แต่ถูกจำกัดด้วยเพดาน FPR** ถ้าจะดัน recall เป็น 90% ต้องจ่าย
**FPR 11.75%** ซึ่งเกินเพดาน 5% ที่โปรเจกต์กำหนด → เป็นการแลกเปลี่ยน (trade-off) ที่เลือกไม่ทำ
ไม่ใช่ความล้มเหลวของโมเดล

**scanning (87.17%)** — เป็นจุดอ่อนจริงคนละเรื่อง (บน TCP 99.8% ก็ยังได้ 87.25%) ไม่ควรเอาสองข้ออ้าง
ข้างบนมากลบ

### 5.4 จุดอ่อนกับ UDP โดยรวม
- สัดส่วน UDP ในชุดฝึกน้อยกว่าชุดทดสอบ (8.87% vs 16.68%)
- `DNS_QUERY_ID` เป็นเลขสุ่ม 16 บิตแบบ uniform **โดยธรรมชาติ** → โมเดลทำนายไม่ได้ (ไม่มีโครงสร้าง)
  การตัดฟิลด์ DNS ออกช่วย FPR แค่ 0.42 จุด → ไม่คุ้ม

## 6. ประเด็นเชิงลึกของชุดข้อมูลและการวัดผล

### 6.1 Artifact ของตัวนับ 32 บิตใน duration
72.8% ของโฟลว์ ddos มีค่า `FLOW_DURATION_MILLISECONDS` ใกล้ **4,294,935 ms** ซึ่งคือการ **wrap
ของตัวนับ 32 บิต** (2³² − 1 ≈ 4.29×10⁹) ไม่ใช่ duration จริง — ddos ที่ตัดแถวเหล่านี้ออกยังจับได้ 96.11%
แสดงว่าโมเดลไม่ได้พึ่งพา artifact นี้

### 6.2 `L7_PROTO` ไม่ถูกจำแนกบน 97.5% ของ UDP/53
2.31M จาก 2.37M แถว UDP/53 มี `L7_PROTO = 0` (Unknown) ในชุดฝึก ขณะที่ nDPI รุ่นปัจจุบันจำแนก DNS ได้
→ เกิด skew ระหว่างชุดฝึกกับ sensor ปัจจุบัน ทำให้ FPR ขยับ (วัดได้ ~5.44% จากเกณฑ์เดิม) — ต้องปรับเทียบ
threshold ใหม่สำหรับทราฟฟิกสด

### 6.3 ทำไมไม่ใช้ accuracy (ปัญหา base-rate)
ที่อัตราการโจมตีจริง ~5% (ไม่ใช่สมดุล 50/50 ในชุดทดสอบ) **precision ตกจาก 99.05% เหลือ 48.15%**
ขณะที่ recall และ FPR *ไม่เปลี่ยน* (เป็นคุณสมบัติของตัวจำแนก ไม่ขึ้นกับ base rate) → accuracy หลอกตา
ในข้อมูลไม่สมดุล จึงรายงานด้วย recall/FPR/precision แยก และยึด **87.59% recall ที่ 4.97% FPR**
เป็นตัวเลขหลักบนชุดทดสอบเต็ม

## 7. การค้นพบ domain shift และการฝึกซ้ำต่อเครือข่าย

### 7.1 การค้นพบ: โมเดลจัดลำดับกลับด้านบนเครือข่ายใหม่
เมื่อนำโมเดลที่ฝึกบน NF-ToN-IoT-v2 ไปรันบนเครือข่ายจำลอง (Mininet) ได้ **AUROC = 0.000** —
ไม่ได้แปลว่าแยกไม่ออก แต่แยกได้สมบูรณ์ใน **ทิศทางกลับ**: ทราฟฟิกปกติได้คะแนนผิดปกติสูงกว่าการโจมตี

### 7.2 สาเหตุเชิงหลักการ
reconstruction error วัด "ห่างจากค่าเฉลี่ยของชุดฝึกเท่าไร" แต่ **ทิ้งข้อมูลทิศทาง** ฟีเจอร์
`SRC_DISTINCT_DST_PORTS_LAST_W` แยกการสแกนจากปกติได้ชัด (2.6σ) แต่เนื่องจาก NF-ToN-IoT-v2 เต็มไปด้วย
การสแกน การสแกนบน Mininet จึง *ใกล้ค่าเฉลี่ยของชุดฝึกมากกว่า* ทราฟฟิกปกติของ Mininet → ฟีเจอร์ที่
ออกแบบมาจับสแกนกลับ *ลด* error ของสแกน นี่คือรากของการจัดลำดับกลับด้าน

> บทเรียนเชิงหลักการ: **autoencoder รู้แค่ "ไม่เหมือนที่เคยเห็น" ไม่ได้รู้ว่า "เป็นการโจมตี"** ถ้า
> เครือข่ายเป้าหมายมีนิยามของ "ปกติ" ต่างจากชุดฝึก ความสัมพันธ์ระหว่างสองอย่างนี้พลิกได้

### 7.3 ทางแก้: ฝึกซ้ำด้วยทราฟฟิกของเครือข่ายเป้าหมาย
ฝึก autoencoder โครงสร้างเดิมใหม่ด้วยทราฟฟิกปกติของเครือข่ายนั้นเอง → **AUROC กลับเป็น ~1.0,
recall ~100%, FPR ต่ำกว่าเพดาน** ยืนยันว่าเป็นเรื่องของการฝึกให้ตรงเครือข่าย ไม่ใช่ข้อจำกัดของวิธีการ
พิสูจน์ซ้ำทั้งบน Mininet และ GNS3 (ใช้ VM Alpine Linux เป็น OS จริง) — ดู
[mininet-live-demo.md](guides/mininet-live-demo.md) และคู่มือ [gns3-setup.md](../network_simulation/gns3/gns3-setup.md)

### 7.4 ข้อค้นพบย่อย: brute-force เป็นขอบเขตของ flow-based detection
บน GNS3 ที่ benign ไม่มี SSH ปกติ brute-force ถูกจับได้ แต่โดยหลักการแล้ว brute-force บนเครือข่ายที่
*มี* SSH ปกติเป็น "คอนเนคชันปกติซ้ำ ๆ" ที่หน้าตาระดับโฟลว์เกือบเหมือน SSH ปกติ → ต้องอาศัย
**ชั้นรวมกลุ่มเชิงพฤติกรรม (alert aggregation, โมดูล 6 — pattern repeated/fan-in)** จึงจับได้
เป็นเหตุผลเชิงสถาปัตยกรรมว่าทำไมระบบต้องมีทั้งชั้น per-flow และชั้น aggregation

## 8. ความสามารถในการอธิบายด้วย SHAP

### 8.1 สิ่งที่อธิบาย
ใช้ **Kernel SHAP** อธิบายว่าแต่ละฟีเจอร์ดัน/ดึง **ค่า reconstruction error** ของโฟลว์นั้นไปเท่าไร
(ไม่ใช่ความน่าจะเป็นของคลาส เพราะโมเดลเป็น autoencoder) background set = ตัวอย่างแถว benign จากชุดฝึก
สุ่มด้วย reservoir sampling เรียกแบบ on-demand ผ่าน `POST /explain/{flow_id}` เท่านั้น (Kernel SHAP แพง)

### 8.2 การประเมินคุณภาพคำอธิบาย (ไม่ใช่แค่แปะ SHAP)
วัดด้วยตัวเลข 4 ด้าน:
- **Local Accuracy** — `base_value + Σshap = reconstruction_error` → residual สูงสุด **1.1e-17**
  (ระดับ floating point เท่านั้น) = ผ่านสมบูรณ์
- **ความนิ่ง (stability)** — รัน SHAP บนโฟลว์เดิมหลายครั้ง ดูว่า top-5 ฟีเจอร์ตรงกันแค่ไหน
- **ความแม่นเทียบค่าลู่เข้า (reference 20,000 samples)** — Spearman: ที่ 100 = 0.38, ที่ 2,000 = 0.77
- **การทดสอบ masking ที่ใช้ไม่ได้** — บันทึกไว้ว่าทำไม (เวกเตอร์ผสมหลุด manifold + Shapley เป็นค่าเฉลี่ย
  ทุกลำดับ) แล้วเปลี่ยนไปใช้วิธีเทียบ reference แทน

### 8.3 การปรับ nsamples
ค่าเริ่มต้น `nsamples = 100` ให้คำอธิบายไม่นิ่ง (sign-flip 75% — ฟีเจอร์เดียวกันรอบหนึ่งบอกดัน error
ขึ้น อีกรอบบอกดึงลง) จึงขึ้นเป็น **2,000** (sign-flip ลดเหลือ 35%, ~164  ms/flow) ไม่ไป 5,000 เพราะ
กินแรมเกิน 1.2 GB (ชนงบ Raspberry Pi) — ปรับได้ผ่าน env `NIDS_SHAP_NSAMPLES`
