### 2.1 การวัดทรัพยากร

วัดบน Intel Core i5-11320H · 4 คอร์ 8 เธรด · RAM 15.4 GB

| ขั้นตอน | ความเร็ว |

**คอขวดอยู่ที่การสกัดโฟลว์ ห่างจากแบบจำลอง 240 เท่า** การเร่งแบบจำลองไม่มีประโยชน์

— **ยืนยันว่าการเลือกใช้ PyTorch แบบ CPU-only ใน Docker เป็นการตัดสินใจที่ถูกต้อง**

ทดสอบบนทรัพยากรจำกัด: ที่งบประมาณ CPU เพียง 1 คอร์ ยังสกัดได้ **1,829 flow/วินาที**

## 4. การทดสอบระบบทั้ง 6 โมดูลบนเครือข่ายจำลอง

### 4.1 สภาพแวดล้อมที่สร้างขึ้น

ติดตั้งเครื่องเสมือน Ubuntu 22.04 (KVM) พร้อม Mininet และ Ryu SDN Controller

```
Ryu Controller (OpenFlow :6653 · REST :8080)
                    │
              switch s1 (OpenFlow 1.3)
    ┌────────┬───────┼────────┬──────────┐
 10.0.1.0/24  10.0.2.0/24  10.0.3.0/24  10.0.4.0/24
 iot1-iot4    srv1,srv2     atk1        nids1 ◄── SPAN port
```

**เพิ่มโฮสต์เฝ้าระวัง `nids1` และพอร์ตสำเนาทราฟฟิก (SPAN)** ซึ่งเดิมยังไม่มีในโค้ด
โดยวางบนซับเน็ตแยกเพื่อไม่ให้ทราฟฟิกของตัวเซนเซอร์ปนในข้อมูลที่เก็บ

**เลือกใช้พอร์ตสำเนาแทนการวางขวางเส้นทาง (inline)** ทำให้ข้อจำกัด "ห้ามบล็อกทราฟฟิกอัตโนมัติ"
ของโครงงานถูกบังคับใช้ในระดับกายภาพ ไม่ใช่เพียงข้อตกลงในโปรแกรม

### 4.2 ผลการทดสอบ — ระบบทำงานครบวงจร

สกัดโฟลว์ได้ **56 รายการ** จากทราฟฟิกจริง ผ่านการเตรียมข้อมูล การตรวจจับ
และบันทึกลงฐานข้อมูล **โดยไม่มีข้อผิดพลาด** และตรวจสอบได้ว่าดึงกฎไฟร์วอลล์
จากตัวควบคุมจริงผ่าน REST API ได้ 9 กฎ

**นี่เป็นครั้งแรกที่โมดูลสกัดโฟลว์ถูกทวนสอบกับแพ็กเกจจริง** เดิมโครงงานไม่มีไฟล์ pcap เลย

### 4.3 ข้อค้นพบสำคัญ — แบบจำลองจัดลำดับกลับด้าน

แบบจำลองจัดให้โฟลว์ทั้งหมดเป็นความผิดปกติ และเมื่อทดสอบด้วยทราฟฟิกผสม
(ปกติ 80 โฟลว์ + สแกนพอร์ต 82 โฟลว์)

| | ค่าความคลาดเคลื่อน (มัธยฐาน) | ช่วง |
|---|---|---|
| ทราฟฟิกปกติ | 0.0491 | 0.0278 – 0.0724 |
| **การสแกนพอร์ต** | **0.0125** | 0.0103 – **0.0186** |

```
AUROC = 0.000
```

**ค่าสูงสุดของการสแกนยังต่ำกว่าค่าต่ำสุดของทราฟฟิกปกติ** ไม่มีค่าขีดแบ่งใดใช้ได้

### 4.4 สาเหตุ — ค่าความคลาดเคลื่อนเก็บระยะทางแต่ไม่เก็บทิศทาง

ตรวจสอบคุณลักษณะที่สกัดได้พบว่า **โมดูลสกัดโฟลว์ทำงานถูกต้อง**
(ไม่มีคุณลักษณะใดเป็นศูนย์ทั้งหมด ไม่มีค่าที่ไม่จำกัด)

คุณลักษณะเชิงพฤติกรรมที่พัฒนาขึ้นเองแยกแยะได้ถูกต้อง:

| | ทราฟฟิกปกติ (z) | การสแกน (z) |
|---|---|---|
| `SRC_DISTINCT_DST_PORTS_LAST_W` | **−2.55** (≈2 พอร์ต) | **+0.09** (≈41 พอร์ต) |

**แยกได้ห่างถึง 2.6 ส่วนเบี่ยงเบนมาตรฐาน** แต่ Autoencoder วัดระยะห่างจากค่าเฉลี่ยของชุดฝึก
โดยไม่พิจารณาทิศทาง และค่า +0.09 ของการสแกน**อยู่ใกล้ค่าเฉลี่ยของชุดฝึกมากกว่า** −2.55
ของทราฟฟิกปกติ (ชุดข้อมูล NF-ToN-IoT-v2 มีการสแกนอยู่มาก ค่าเฉลี่ยจึงสูงถึง 40.2 พอร์ต)

**คุณลักษณะที่ออกแบบมาเพื่อจับการสแกน จึงกลับไปลดค่าความผิดปกติของการสแกน**

### 4.5 การแก้ไข — ฝึกใหม่ด้วยทราฟฟิกของเครือข่ายเป้าหมาย

ฝึก Autoencoder สถาปัตยกรรมเดียวกัน (46→128→64) ด้วยทราฟฟิกปกติของเครือข่ายจำลอง
เพียง **40 โฟลว์**

| | ชุดข้อมูลเดิม | **ฝึกใหม่** |
|---|---|---|
| AUROC | **0.000** | **1.000** |
| Recall | 0% | **100%** |
| ค่าความคลาดเคลื่อนของการสแกน | ต่ำกว่าทราฟฟิกปกติ | **สูงกว่า 3 ล้านเท่า** |

**สรุป: ไม่ใช่ข้อจำกัดของวิธีการ แต่เป็นความจำเป็นในการฝึกให้ตรงกับเครือข่ายเป้าหมาย**
ซึ่งไม่ต้องใช้ข้อมูลการโจมตีที่ติดป้ายกำกับเลย อันเป็นข้อได้เปรียบหลักของวิธีการแบบไม่มีผู้สอน

> **ข้อจำกัดของการทดลอง:** ฝึกด้วยเพียง 40 โฟลว์ · FPR 7.5% ยังเกินเป้าหมาย 5% ·
> ทราฟฟิกสังเคราะห์ทำให้สองกลุ่มแยกจากกันง่ายกว่าความเป็นจริง
> **ค่า AUROC 1.000 นี้ไม่สามารถนำไปเทียบกับ 87.59% บนชุดข้อมูลจริงได้**

## 5. ส่วนที่พัฒนาเพิ่มเติม

### 5.1 การรวมกลุ่มการแจ้งเตือน (Alert Aggregation)

จากการคำนวณพบว่าที่อัตราผลบวกลวง 4.97% เครือข่ายที่มีโฟลว์ 100,000 รายการต่อวัน
จะสร้างการแจ้งเตือนประมาณ **9,100 รายการต่อวัน** ซึ่งเกินกว่าผู้ดูแลจะตรวจสอบได้

พัฒนาส่วนรวมกลุ่มโดยใช้มิติเดียวกับคุณลักษณะเชิงพฤติกรรมที่ออกแบบไว้
ทดสอบบนหมายเลขไอพีจริงจากชุดข้อมูล: **1,214,080 โฟลว์ → 726 เหตุการณ์**
พร้อมหน้าจอแสดงผลบนแดชบอร์ด

### 5.2 การทดลองค่าขีดแบ่งแยกตามโปรโตคอล — ผลเป็นลบ

ทดลองแยกค่าขีดแบ่งระหว่าง TCP และ UDP พบว่า

| นโยบาย | Recall | FPR |
|---|---|---|
| ค่าเดียว (ปัจจุบัน) | 87.59% | 4.97% |
| แยกตามโปรโตคอลให้ FPR เท่ากัน | **86.36%** | 4.96% |
| จัดสรรงบประมาณผลบวกลวงแบบเหมาะที่สุด | 87.72% | 4.97% |

การกำหนดให้ FPR เท่ากันทุกโปรโตคอล**ลดอัตราการตรวจจับคลาส dos ลง 18.9 จุด**
ส่วนวิธีที่ดีที่สุดได้ผลดีขึ้นเพียง 0.13 จุด **จึงคงใช้ค่าขีดแบ่งเดียวตามเดิม**

### 5.3 การเตรียมความพร้อมสำหรับการใช้งานจริง

- จัดทำคู่มือการติดตั้งและการฝึกแบบจำลองใหม่สำหรับเครือข่ายใหม่
- เพิ่มการแสดงผลบนแดชบอร์ดว่าแบบจำลองใดกำลังให้บริการและฝึกเมื่อใด
- เพิ่มตัวบ่งชี้การเบี่ยงเบน (drift) โดยเทียบอัตราความผิดปกติที่สังเกตได้กับค่าที่ปรับเทียบไว้
