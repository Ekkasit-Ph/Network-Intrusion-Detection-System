## ข้อ 2 — Feature เชิงพฤติกรรม (สไลด์ 8)

อาจารย์ขีดเส้นใต้หัวข้อ และวงกล่องที่เขียนว่า *"นี่คือส่วนที่แสดงว่าเราคิดเอง"*
→ **อาจารย์เห็นว่าตรงนี้คือจุดขาย และอยากให้ขยาย**

**สิ่งที่ควรเพิ่ม:**
1. ยกตัวอย่างเป็นรูปธรรม — เครื่องสแกนติดต่อ 30 ปลายทางใน 50 โฟลว์ เทียบกับเครื่องปกติที่ติดต่อ 2–3
2. อธิบายว่าทำไมต้องเป็น **หน้าต่างเลื่อน 50 โฟลว์** ไม่ใช่ค่าสะสม (ป้องกันโมเดลจำว่า "นี่คือเครื่องไหน")
3. **หลักฐานเชิงตัวเลข** — การทดลองเพิ่มฟีเจอร์ทีละขั้นได้ recall 29.59% → 45.87% ที่ FPR เท่ากัน
4. ⚠️ เตรียมรับมือ: ถ้าดู ablation ทีละฟีเจอร์ ฟีเจอร์ทั้งสามอยู่อันดับ 20/26/30 จาก 46
   ต้องอธิบายว่า ablation ทีละตัว**ประเมินฟีเจอร์ที่สัมพันธ์กันต่ำกว่าความจริง**
   หลักฐานที่ควบคุมตัวแปรได้จริงคือการทดลองเพิ่มทีละขั้นในข้อ 3

## ข้อ 3 — ทำไมแต่ละคลาสตรวจจับได้ไม่เท่ากัน (สไลด์ 12)

**คำตอบหลัก: ขึ้นกับว่าเป็น TCP หรือ UDP**

| คลาส | TCP | UDP | recall รวม |
|---|---|---|---|
| password | 99.8% | 0.2% | 99.10% |
| ddos | ~100% | ~0% | 98.88% |
| injection | 94.9% | 5.1% | 92.55% |
| **dos** | 14.5% | **85.5%** | **80.81%** |
| **xss** | 49.0% | **51.0%** | **74.04%** |

**เหตุผล:** 5 ฟีเจอร์เป็นของ TCP โดยเฉพาะ (TCP_FLAGS, CLIENT/SERVER_TCP_FLAGS,
TCP_WIN_MAX_IN/OUT) พอเจอ UDP ค่าเป็น 0 ทั้งหมด **100.00%** ไม่มีข้อยกเว้น
→ ไม่มีร่องรอย handshake ให้ดู เหลือแค่ "กี่ไบต์ กี่แพ็กเก็ต"

**สองกรณีที่ต้องแยกอธิบาย:**

**xss (74.04%) — ไม่ใช่จุดอ่อนของโมเดล แต่เป็น label noise**
- เฉพาะ flow TCP ตรวจจับได้ **99.35% สูงที่สุดในทุกคลาส**
- flow UDP ในคลาสนี้มี L7_PROTO = "Unknown" **100.0%** เหมือน benign UDP ทุกประการ
- XSS วิ่งบน HTTP ซึ่งต้องเป็น TCP เสมอ → flow UDP 65 ไบต์ **เป็น XSS ไม่ได้ในทางเทคนิค**
- error แยกเป็นสองกลุ่มขาดจากกัน (ที่หลุด p95=0.00102, ที่จับได้ p5=0.00275) = คนละประชากร

**dos (80.81%) — จุดอ่อนจริง แต่ชนเพดาน FPR**
- flow เล็กมาก: 1 แพ็กเก็ตไป-กลับ 63–71 ไบต์ duration 0 → ต่างจาก benign แค่ 2 ฟีเจอร์
- ddos ต่างจาก benign พร้อมกัน 6+ ฟีเจอร์ → error 3.42× threshold ส่วน dos แค่ 1.35×
- ที่หลุดกับที่จับได้เป็นทราฟฟิกชนิดเดียวกัน error แค่ตกคนละฝั่งเส้น
- **ถ้าจะดันเป็น 90% ต้องจ่าย FPR 11.75%** ซึ่งเกินเพดาน 5% ที่ตั้งไว้

**scanning (87.17%) — อย่าเอาสองข้ออ้างข้างบนมาใช้** เป็น TCP 99.8% และบน TCP
ก็ยังได้แค่ 87.25% นี่คือจุดอ่อนจริงคนละเรื่อง

## ข้อ 4 — แดชบอร์ด (สไลด์ 15)

### 4.1 แก้โค้ด: แสดงตัวที่ทำให้ error เป็นบวก

**ตอนนี้** [`app.js:306`](../../web/frontend/app.js#L306) เรียงตาม `Math.abs(val)` แล้วตัด 8 อันดับแรก
→ รายการบนสุดปนทั้งตัวที่**ดัน**ค่า error ขึ้น (บวก) และตัวที่**ดึง**ลง (ลบ)

**สิ่งที่อาจารย์ต้องการ** — คนดูแลระบบถามว่า *"ทำไมโฟลว์นี้ถึงถูกแจ้งเตือน"*
คำตอบคือฟีเจอร์ที่**ดันค่าขึ้น**เท่านั้น ตัวที่ดึงลงไม่ใช่เหตุผลของการแจ้งเตือน

**การแก้:** เรียงตามค่าจริงจากมากไปน้อย (ไม่ใช่ค่าสัมบูรณ์) ให้ตัวบวกขึ้นก่อน
และใช้สีส้ม `--color-accent` ซึ่งโค้ดใช้อยู่แล้วสำหรับค่าบวก ส่วนค่าลบยังเก็บไว้ดูได้
ในโหมด "Show all 46 features"

### 4.2 ขยายคำอธิบายการแสดงผล

ควรอธิบายทีละองค์ประกอบว่าแต่ละอย่าง**ตอบคำถามอะไรของคนใช้งาน**:

| องค์ประกอบ | ตอบคำถาม |
|---|---|
| แถบเทียบค่าความคลาดเคลื่อนกับขีดแบ่ง | เกินเส้นไปเท่าไร (กี่เท่าของ threshold) |
| ค่าฟีเจอร์ก่อน scale | ค่าจริงคือเท่าไร ไม่ใช่ค่า z ที่คนอ่านไม่รู้เรื่อง |
| แถบ SHAP สีส้ม | ฟีเจอร์ไหนทำให้ถูกแจ้งเตือน |
| สมการ base + Σshap = error | ตรวจสอบได้ว่าคำอธิบายเชื่อถือได้จริง (Local Accuracy) |
| แท็บ Firewall gaps | โฟลว์ผิดปกติที่ไฟร์วอลล์ยังปล่อยผ่าน = ช่องโหว่ที่ต้องปิด |
