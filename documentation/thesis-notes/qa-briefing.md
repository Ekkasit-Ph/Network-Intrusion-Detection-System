# ข้อมูลระบบทั้งหมด สำหรับตอบคำถาม

ทุกตัวเลขในเอกสารนี้ดึงจากโค้ดและไฟล์ผลลัพธ์จริง ตรวจแล้ว ณ วันที่เขียน

---

# ⚠️ อ่านส่วนนี้ก่อน — 5 คำถามที่ตอบผิดแล้วเสียหาย

## 1. "คุณลักษณะที่พัฒนาเอง 3 ตัว สำคัญจริงหรือ"

**ข้อมูลที่อาจถูกยกมาแย้ง:** ถ้าวัดด้วยการตัดคุณลักษณะทีละตัวออกจากโมเดลสุดท้าย
แล้วดูว่า AUC ตกเท่าไร ทั้งสามตัวอยู่**อันดับ 20, 26 และ 30 จาก 46**

| คุณลักษณะ | อันดับ | AUC ตกลง |
|---|---|---|
| SRC_DISTINCT_DST_PORTS_LAST_W | 20 | 0.168 |
| SRC_DISTINCT_DST_IPS_LAST_W | 26 | 0.076 |
| DST_DISTINCT_SRC_IPS_LAST_W | 30 | 0.022 |

**คำตอบที่ถูกต้อง:** การตัดทีละตัวกับการเพิ่มทั้งชุด **วัดคนละอย่าง**

ในโมเดลที่มีคุณลักษณะ 46 ตัวซึ่งสัมพันธ์กันเอง การตัดออกทีละตัวจะ**ประเมินความสำคัญ
ต่ำกว่าจริง** เพราะคุณลักษณะอื่นชดเชยกันได้บางส่วน

หลักฐานที่แท้จริงคือการทดลอง**เพิ่มทั้งสามตัวพร้อมกัน** ซึ่งทำให้ Recall เพิ่มจาก
**ร้อยละ 29.59 เป็น 45.87** วัดบนชุดทดสอบเดียวกัน คุมค่า FPR ที่ประมาณร้อยละ 5 เท่ากัน
นั่นคือการเปรียบเทียบที่ควบคุมตัวแปรแล้ว

> **ห้ามพูดว่า "สามตัวนี้สำคัญที่สุด"** เพราะข้อมูลไม่รองรับ ให้พูดว่า
> "การเพิ่มทั้งสามตัวทำให้ recall เพิ่ม 16 จุด" ซึ่งเป็นสิ่งที่วัดมาจริง

## 2. "ระบบตรวจจับการโจมตีได้ใช่ไหม"

**ตอบ:** ไม่ใช่ครับ ระบบแยกได้แค่ **ปกติ / ผิดปกติ** เท่านั้น
การตัดสินว่าเป็นการโจมตีหรือไม่ เป็นหน้าที่ของผู้ดูแลระบบโดยดูจากผล SHAP

ตรงกับข้อจำกัดข้อ 1.3.2 ข้อ 1 ที่ระบุไว้เอง **ถ้าพูดผิดตรงนี้จะขัดกับเล่มตัวเอง**

## 3. "Precision 48% ในสภาพจริง ใช้งานได้หรือ"

**ตอบ:** ระบบออกแบบเป็น**กลไกตรวจสอบเชิงรับ**ที่ให้ผู้ดูแลระบบตัดสินขั้นสุดท้าย
ไม่ใช่ระบบบล็อกอัตโนมัติ

SHAP คือส่วนที่ทำให้การคัดกรองการแจ้งเตือนผิดพลาดทำได้เร็ว — ผู้ดูแลระบบเห็นได้ทันที
ว่าโฟลว์นั้นถูก flag เพราะคุณลักษณะใด และตัดสินได้เร็วกว่าการไล่ดูข้อมูลดิบ
นี่คือเหตุผลที่โครงงานให้ความสำคัญกับการอธิบายผลตั้งแต่ต้น

และเป็นเหตุผลว่าทำไม**เพดาน FPR ร้อยละ 5 จึงเป็นข้อกำหนดที่สำคัญที่สุด** — ถ้า FPR
เป็นร้อยละ 10 จำนวนการแจ้งเตือนผิดจะเพิ่มเป็นเท่าตัวทันที

## 4. "ใช้ ensemble หรือโมเดลเดียว"

**ตอบ:** โมเดลเดียวครับ

โค้ดรองรับการทำ ensemble และมีชุดทดสอบครอบคลุมแล้ว แต่**โมเดลที่ใช้จริงในระบบ
เป็นโมเดลเดียว** เพราะยังไม่ได้ฝึก ensemble สำหรับสถาปัตยกรรมสุดท้าย
ระบบจะใช้ ensemble โดยอัตโนมัติถ้ามีไฟล์อยู่ ไม่ต้องแก้โค้ดอื่น

> **ห้ามพูดว่าใช้ ensemble** ถ้าไม่ได้ฝึกจริง

## 5. "ทดสอบบนสภาพแวดล้อมจำลองแล้วหรือยัง"

**ตอบ:** ยังครับ เขียนโค้ดไว้แล้วแต่ยังไม่ได้รันจริง

เหตุผล: Mininet ต้องใช้สิทธิ์ root และแพ็กเกจระดับระบบปฏิบัติการ ส่วน Ryu ยังไม่รองรับ
Python รุ่นที่ใช้พัฒนา ส่วนที่ทดสอบแล้วคือ**ส่วนที่เชื่อมกับโมดูลที่ 6** คือการอ่านกฎ
รูปแบบ Ryu flow table และ iptables ซึ่งมีชุดทดสอบ 37 กรณี

**ขนาด 114 KB กับ 28,526 พารามิเตอร์ เป็นตัวเลขที่ดีมากสำหรับการอ้างเรื่องความเบา**
ใช้ตอบคำถามว่า "เบาจริงหรือ" ได้ทันที

## ทำไมต้อง Denoising

ชั้นแฝง **64 มิติ มากกว่าอินพุต 46 มิติ** (overcomplete) ซึ่งตามทฤษฎีโมเดลสามารถ
คัดลอกข้อมูลผ่านไปยังเอาต์พุตได้โดยไม่ต้องเรียนรู้อะไรเลย

การเติมสัญญาณรบกวนที่อินพุตแต่คำนวณค่าความคลาดเคลื่อนเทียบกับข้อมูลต้นฉบับ
บังคับให้โมเดลต้องเรียนรู้โครงสร้างที่แท้จริงเพื่อกำจัดสัญญาณรบกวนออก

**เชื่อมกับบทที่ 2:** Song et al. (2021) ระบุว่าขนาดชั้นแฝงเป็นปัจจัยวิกฤต หากใหญ่เกินไป
จะ overfit — โครงงานนี้แก้ด้วยการเติมสัญญาณรบกวน แทนการลดขนาดชั้นแฝง
ซึ่งจะทำให้สูญเสียข้อมูลสำคัญ

## การปรับจูน

- ไลบรารี **Optuna** อัลกอริทึม Tree-structured Parzen Estimator
- **50 รอบการทดลอง**
- เป้าหมายการค้นหา: **Recall ณ จุดที่ FPR ≤ 5%** ไม่ใช่ ROC-AUC
- ROC-AUC บน validation ของโมเดลที่ได้: 0.9586

**ทำไมไม่ใช้ ROC-AUC เป็นเป้าหมาย:** AUC วัดตลอดทั้งเส้นโค้ง แต่ระบบใช้งานที่จุดเดียว
โมเดลที่ AUC สูงกว่าอาจให้ recall ที่จุดทำงานจริงต่ำกว่า นี่เป็นปัจจัยสำคัญที่สุด
ที่ทำให้ประสิทธิภาพเพิ่ม

## ฟังก์ชันความคลาดเคลื่อน

MSE เฉลี่ยทุกคุณลักษณะ ต่อหนึ่งโฟลว์

## ทำไม percentile ไม่ใช่ KDE หรือ μ+kσ

- **μ+kσ** ตั้งสมมติฐานว่าค่าแจกแจงแบบปกติ แต่ค่า reconstruction error **เบ้ขวา**
  (ต่ำสุดที่ศูนย์ ไม่มีขีดจำกัดบน) วิธีนี้จึงประเมินเกณฑ์คลาดเคลื่อน
- **KDE** (แนวทางของ Kim et al. 2025) ให้ผลดีแต่ต้นทุนการคำนวณสูงกว่า
  ขัดกับหลักการความเบาของโครงงาน
- **percentile** ไม่ตั้งสมมติฐานเรื่องรูปร่างการแจกแจง และคำนวณเร็ว

ตำแหน่ง KDE ปรากฏอยู่ในกราฟ ROC และ PR ในเล่มแล้ว เพื่อเปรียบเทียบ

# 6. SHAP

| รายการ | ค่า |
|---|---|
| วิธี | `shap.KernelExplainer` |
| กลุ่มอ้างอิง (background) | **100 แถว** สุ่มจากข้อมูล**ปกติ**ในชุดฝึกสอน |
| nsamples ต่อการอธิบาย | 100 |
| **เวลาที่วัดได้จริง** | **8–28 ms** (ค่ากลาง 24 ms) |
| ค่าคลาดเคลื่อนคงเหลือ | **0.000000** |
| เรียกใช้เมื่อ | ผู้ดูแลระบบร้องขอเท่านั้น |

> **แก้จากบทพูด** — บทเดิมเขียนว่า "23 มิลลิวินาที ถึงไม่กี่วินาที" ค่าจริงที่วัดได้คือ
> **8–28 มิลลิวินาที** ให้พูดว่า "ไม่เกิน 30 มิลลิวินาทีต่อโฟลว์" ซึ่งดีกว่าและตรงกว่า

**ทำไม Kernel ไม่ใช่ Deep หรือ Tree**
- Tree SHAP ออกแบบมาเฉพาะโมเดลตระกูลต้นไม้ ใช้กับออโตเอนโค้ดเดอร์ไม่ได้
- Kernel SHAP เป็น model-agnostic ไม่ต้องเข้าถึงโครงสร้างภายในโมเดล
- ตรงกับที่ระบุไว้ในบทที่ 2 หัวข้อ 2.1.4 และบทที่ 3 หัวข้อ 3.1.2

**สิ่งที่ SHAP อธิบายในโครงงานนี้**
ไม่ใช่ผลการจำแนกประเภท แต่เป็น**คะแนนความผิดปกติ** คือค่าความคลาดเคลื่อน
ในการสร้างใหม่ ว่าคุณลักษณะใดผลักให้ค่านี้สูงขึ้นจากค่าพื้นฐาน

**การแสดงค่าจริง**
ระบบเก็บค่า z-score จึงย้อนกลับด้วยค่าเฉลี่ยและส่วนเบี่ยงเบนมาตรฐานของชุดฝึกสอน
ตรวจสอบความถูกต้องของการย้อนกลับแล้ว ได้ค่าคลาดเคลื่อนระดับ **1e-15**
(เท่ากับความละเอียดของเลขทศนิยม)

# 8. ระบบและสถาปัตยกรรม

## องค์ประกอบ

| ส่วน | เทคโนโลยี |
|---|---|
| Backend | FastAPI |
| ฐานข้อมูล | **SQLite** |
| Frontend | HTML / CSS / JavaScript ล้วน ไม่มีเฟรมเวิร์ก ไม่มี build step |
| กราฟ | SVG วาดโดยตรง ไม่ใช้ไลบรารีภายนอก |
| การรับข้อมูล | **HTTP polling ทุก 2 วินาที** |
| การติดตั้ง | Docker (CPU-only PyTorch) |

## เส้นทางข้อมูล — จุดที่มักเข้าใจผิด

**กระบวนการตรวจจับเขียนลงฐานข้อมูลโดยตรง ไม่ผ่าน API**

โมดูล 1–3 ทำงานรวมกันเป็นกระบวนการเดียว (`live_capture.py`) แล้วเขียนลง SQLite
ส่วน FastAPI ทำหน้าที่**อ่าน**เป็นหลัก มีทางเขียนทางเดียวคือ `POST /explain/{flow_id}`

**มีกระบวนการที่เขียนฐานข้อมูล 3 ตัว**
1. `live_capture.py` → ตาราง flows
2. `replay_demo.py` → flows + replay_ground_truth
3. `ryu_log_compare.py` → firewall_checks

SQLite จึงเป็น**จุดเชื่อมต่อกลาง** ระหว่างกระบวนการที่ทำงานแยกกัน

## ปลายทางการเรียกใช้ (endpoint)

`/alerts` · `/stats` · `/stats/trend` · `/flow/{id}` · `/meta` · `/firewall-gaps` ·
`POST /explain/{id}`

## ตารางในฐานข้อมูล

`flows` · `replay_ground_truth` · `explanations` · `firewall_checks`

**ทำไมแยก replay_ground_truth ออกจาก flows:** เพราะทราฟฟิกจริงไม่มีเฉลย
ตารางนี้จะว่างเสมอในการใช้งานจริง การเก็บรวมกันจะทำให้ดูเหมือนทุกโฟลว์มีเฉลยได้

## การออกแบบที่ตั้งใจ 3 อย่าง

1. **ช่วงที่ไม่มีทราฟฟิกวาดเป็นลายขวาง ไม่ใช่ 0%** — "ไม่มีข้อมูล" กับ "มีข้อมูลแต่ปกติ"
   เป็นคนละเรื่อง ถ้ารวมกัน เซ็นเซอร์ที่ตายจะดูเหมือนเครือข่ายปลอดภัย
2. **แจ้งเตือนเมื่อไม่มีโฟลว์เกิน 15 วินาที** — ด้วยเหตุผลเดียวกัน
3. **ใช้คำว่า "ผิดปกติ" ไม่ใช่ "การโจมตี"** ทั้งระบบ

# 9. โมดูลที่ 6 — ตรวจสอบไฟร์วอลล์

## รองรับ 2 รูปแบบ

## ตรรกะการจับคู่

| ประเด็น | วิธีจัดการ |
|---|---|
| ฟิลด์ที่ไม่ได้ระบุในกฎ | ถือเป็น wildcard (ตรงทุกค่า) |
| OpenFlow | **รายการ action ว่าง = DROP** (OpenFlow ไม่มี action ชื่อ DROP) |
| ลำดับความสำคัญ | Ryu ใช้ priority สูงชนะ · iptables ใช้ first-match-wins แปลงเป็น priority ลดหลั่น |
| ที่อยู่ที่แปลงไม่ได้ | **ไม่นับว่าตรง** เพื่อไม่ให้รายงานการป้องกันที่ไม่มีอยู่จริง |
| target ที่ไม่ใช่คำตัดสิน (LOG) | ข้าม |

## สามสถานะ

- **GAP** — กฎจะปล่อยผ่าน
- **Covered** — มีกฎบล็อกอยู่แล้ว
- **Insufficient data** — ข้อมูลไม่พอเทียบ **ไม่ได้แปลว่าปลอดภัย**

**ทำไมต้องมีสถานะที่สาม:** นับรวมกับ "ปลอดภัย" = ปกปิดช่องโหว่จริง ·
นับรวมกับ "ช่องโหว่" = สร้างช่องโหว่ที่ไม่มีอยู่ ทั้งสองแย่กว่าการบอกว่าไม่รู้

## ทำไมไม่บล็อกอัตโนมัติ

ระบบมี FPR ประมาณ 5% การต่อเข้ากับการบล็อกอัตโนมัติจะตัดทราฟฟิกปกติ
ราวหนึ่งในยี่สิบ **กลายเป็นการสร้างภาวะปฏิเสธการให้บริการด้วยเครื่องมือที่มีไว้ป้องกัน**

ตรงกับข้อจำกัดข้อ 1.3.2 ข้อ 4
