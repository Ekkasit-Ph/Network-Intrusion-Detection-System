# คู่มือนำไปใช้งานจริง: เริ่มใช้ครั้งแรก และการเทรนใหม่

> **หลักการ: UI สำหรับ "รู้ว่าเมื่อไรต้องเทรน" · CLI สำหรับ "เทรน"**
> ไม่ทำซ้ำการกระทำเดียวกันในสองที่

## ทำไมไม่มีปุ่ม Retrain บนเว็บ

**1. Data poisoning — ข้อนี้สำคัญที่สุด**
การเทรนใหม่ใช้ทราฟฟิกช่วงหลังเป็นนิยามของ "ปกติ" ปุ่มหนึ่งคลิกจึงเท่ากับ**หนึ่งคลิกที่สอนแบบจำลองว่า
การโจมตีที่กำลังเกิดอยู่คือเรื่องปกติ** แล้วมันจะมองไม่เห็นการโจมตีนั้นตลอดไป
ปุ่มไม่มีทางตรวจได้ว่าช่วงเวลานั้นสะอาดจริง ขณะที่ `PROJECT.md` กำหนดไว้ว่า **"ฝึกด้วย benign เท่านั้น"**

**2. เป็นงาน batch ที่ใช้เวลานาน** — 100 epoch บนข้อมูล 4.27 ล้านแถว
ปุ่มที่ไม่มีแถบความคืบหน้า ไม่มีปุ่มยกเลิก ไม่มีทางย้อนกลับ คือกับดัก

**3. การย้อนกลับเป็นงานระดับไฟล์** — ถ้าโมเดลใหม่แย่กว่า ต้องเอาตัวเก่ากลับมา
**พร้อม `scaler.pkl` และ `categorical_encoders.json` ที่เป็นชุดเดียวกัน** สลับผิดคู่แล้วพังแบบเงียบ ๆ

## ก. เริ่มใช้กับเครือข่ายใหม่

**ไม่ต้องมีข้อมูลการโจมตีที่ติดป้ายกำกับเลย** — ดู [PROJECT.md](PROJECT.md) และหัวข้อที่เกี่ยวข้อง

```bash
# 1. เก็บทราฟฟิกปกติ 1-2 สัปดาห์  <- ขั้นที่สำคัญที่สุด ดูหมายเหตุข้างล่าง
#    ต้องมั่นใจว่าช่วงนี้ไม่มีการโจมตีปนอยู่

# 2. เตรียมข้อมูล (สร้าง scaler + encoders ใหม่ ผูกกับเครือข่ายนี้)
python -m source.preprocessing.pipeline --input data/raw/<capture>.csv

# 3. เทรน (benign ล้วน)
python -m source.model.train --artifacts-dir artifacts/models/<ชื่อใหม่>

# 4. ตั้งค่าขีดแบ่ง
python -m source.model.threshold \
  --processed-dir data/processed --artifacts-dir artifacts/models/<ชื่อใหม่>

# 5. เริ่มให้บริการ
NIDS_MODEL_DIR=artifacts/models/<ชื่อใหม่> NIDS_PROCESSED_DIR=data/processed \
  python -m uvicorn web.backend.main:app --port 8000
```

**ต้องมีข้อมูลเท่าไร** — สำหรับ**ขั้นตั้งขีดแบ่ง** วัดแล้วว่า **20,000 flow ก็ได้ความแม่น ±0.15%**
(bootstrap 200 ครั้ง) ส่วนจำนวนที่ต้องใช้**เทรนแบบจำลอง**ยังไม่ได้วัด — ตัวปัจจุบันใช้ 4.27 ล้าน flow

⚠️ **ถ้าไม่มี label เลย** ขั้นที่ 4 จะเลือกขีดแบ่งไม่ได้ตามเกณฑ์ปกติ (ซึ่งใช้ label ของ validation)
ให้ใช้เปอร์เซ็นไทล์ 95 ตรง ๆ ซึ่ง **ให้ FPR = 5% โดยนิยาม** — และข้อเท็จจริงที่น่าสนใจคือ
เกณฑ์ที่ใช้ label อยู่ตอนนี้**ก็เลือก P95 ออกมาพอดี**

## ข. รู้ได้อย่างไรว่าถึงเวลาเทรนใหม่ — ดูจากแดชบอร์ด

ไทล์ **Anomaly rate** แสดงค่าที่สังเกตได้ พร้อมค่าที่ปรับเทียบไว้ใต้ลงมา

```
ANOMALY RATE · 1H
47.4 %
calibrated 5.0%        <- เป็นสีส้มและมีแถบซ้ายเมื่อต่างกันเกิน 3 เท่า
```

ขีดแบ่งถูกตั้งให้ flag ทราฟฟิก**ปกติ** 5% ดังนั้นบนเครือข่ายที่ไม่มีการโจมตี ตัวเลขนี้ควรวนใกล้ 5%

| อ่านได้ว่า | ความหมาย |
|---|---|
| ใกล้ค่าที่ปรับเทียบ | แบบจำลองยังเข้ากับเครือข่าย |
| **สูงกว่ามาก** | กำลังโดนโจมตี **หรือ** เครือข่ายเปลี่ยนไปจนแบบจำลองไม่เข้ากับมันแล้ว |
| **ต่ำกว่ามาก** | ทราฟฟิกเปลี่ยนรูปแบบ หรือตัวเก็บข้อมูลมีปัญหา |

> ⚠️ **แดชบอร์ดไม่ได้บอกว่าอันไหน** เพราะการโจมตีกับ drift ดันตัวเลขนี้ไปทางเดียวกัน
> มันชี้ให้ดู ไม่ได้สรุป — การตัดสินเป็นงานของคน


## ค. เทรนใหม่ (CLI)

```bash
# เทรนลงโฟลเดอร์ใหม่เสมอ อย่าทับของเดิม -- ของเดิมคือแผนสำรอง
python -m source.model.train --artifacts-dir artifacts/models/<วันที่>
python -m source.model.threshold --artifacts-dir artifacts/models/<วันที่>
python -m source.model.evaluate  --artifacts-dir artifacts/models/<วันที่>

# เทียบกับตัวเดิมก่อนสลับ
python -c "
import json
for d in ('optuna-denoising-50','<วันที่>'):
    m=json.load(open(f'artifacts/models/{d}/metrics_report.json'))['overall']
    print(d, 'recall', round(m['attack_class']['recall']*100,2), 'FPR', round(m['fpr']*100,2))"
```

**สลับ:** เปลี่ยน `NIDS_MODEL_DIR` แล้วรีสตาร์ท backend (~1 วินาที)
**ย้อนกลับ:** ชี้ `NIDS_MODEL_DIR` กลับไปที่โฟลเดอร์เดิม แล้วรีสตาร์ท

> **แบบจำลองถูกโหลดครั้งเดียวตอนเริ่มโปรเซส** ([`main.py` lifespan](../web/backend/main.py))
> การเปลี่ยนแบบจำลองจึงต้องรีสตาร์ท **เป็นการตัดสินใจ ไม่ใช่ข้อบกพร่อง** —
> การโหลดใหม่ขณะทำงานต้องจัดการเรื่องคำขอที่ค้างอยู่ และ `scaler` กับ `encoders`
> ต้องเปลี่ยนพร้อมกันเป็นชุด ซึ่งแลกไม่คุ้มกับการรีสตาร์ทที่ใช้เวลา 1 วินาที

## ง. สามความเสี่ยงที่ต้องเขียนในเล่ม

**1. ข้อมูลที่เก็บมาต้องสะอาดจริง** — ถ้ามีการโจมตีปนตอนเก็บ แบบจำลองจะเรียนว่านั่นคือปกติ
นี่คือราคาที่แลกมากับการไม่ต้องใช้ label

**2. Concept drift** — เครือข่ายเปลี่ยน "ปกติ" ก็เปลี่ยน ต้องมีแผนเทรนซ้ำเป็นระยะ

**3. ปริมาณการแจ้งเตือน** — FPR 5% ของ 100,000 flow/วัน = ~4,700 การแจ้งเตือนลวงต่อวัน
ดู [alert-aggregation.md](alert-aggregation.md)

## จ. สิ่งที่ยังไม่มี

- ไม่มีการเฝ้าดู drift แบบอัตโนมัติที่แจ้งเตือนเอง (ต้องมีคนดูแดชบอร์ด)
- ไม่ได้เทียบการกระจายของ error ปัจจุบันกับตอนปรับเทียบ ทั้งที่ข้อมูลมีแล้วใน
  `threshold.json → calibration_reference.benign_error_percentiles` และส่งออกทาง `/meta` แล้ว
  — เป็นงานต่อยอดที่ทำได้ทันที
