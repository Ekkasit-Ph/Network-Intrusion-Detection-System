# ผลการรันท่อทั้ง 6 โมดูลบน Mininet (20 ก.ย. 2569)

ปิดแทร็กที่ 4 จาก 4 ที่ `PROJECT.md` สัปดาห์ 13–15 สัญญาไว้ — **ครบทุกแทร็กแล้ว**

> **นี่คือครั้งแรกที่โมดูล 1 ถูกทวนสอบกับทราฟฟิกจริง** ก่อนหน้านี้ในโปรเจกต์ไม่มีไฟล์ pcap
> แม้แต่ไฟล์เดียว `verify_skew.py` ได้แค่จำลอง skew ด้วยการสลับคอลัมน์

## สิ่งที่รัน

```
Ryu (ryu_app.py) ─ OpenFlow ─ s1 ─┬─ 10.0.1.0/24  iot1..iot4
                                   ├─ 10.0.2.0/24  srv1, srv2 (http)
                                   ├─ 10.0.3.0/24  atk1
                                   └─ 10.0.4.0/24  nids1 ← SPAN port
                                                      └ live_capture (โมดูล 1→3)
```

ทราฟฟิกที่สร้าง: HTTP 9 ครั้ง · ping 9 ครั้ง · **สแกนพอร์ต 8 พอร์ตจาก `atk1` ไป `srv1`**

## ✅ ท่อทำงานครบวงจร

**56 flow** ถูกสกัด → เตรียมข้อมูล → ให้คะแนน → บันทึกลงฐานข้อมูล **โดยไม่มี error**
และเห็นการสแกนของ `atk1 → srv1` ครบ 8 flow

ก่อนหน้านี้ไม่มีอะไรยืนยันได้ว่าทั้ง 6 โมดูลต่อกันติดจริง — ตอนนี้มี

## 🔴 แต่โมเดลตัดว่าผิดปกติ 100%

| กลุ่ม | จำนวน | ผิดปกติ | error มัธยฐาน |
|---|---|---|---|
| **IPv6 (ICMPv6 multicast)** | 36 | **100%** | **345× threshold** |
| **IPv4 (ทราฟฟิกที่เราสร้าง)** | 20 | **100%** | **14× threshold** |

### และข้อที่ร้ายแรงที่สุด — การโจมตีได้คะแนน *ต่ำกว่า* ทราฟฟิกปกติ

| ทราฟฟิก | error |
|---|---|
| `iot1 → srv1:80` HTTP (ปกติ) | **14–15× threshold** |
| `iot1 → srv1` ICMP (ปกติ) | **53–55× threshold** |
| **`atk1 → srv1:21,22` การสแกนพอร์ต** | **7–9× threshold** ← ต่ำที่สุด |

**ลำดับความผิดปกติกลับหัว** — ถ้าผู้ดูแลเรียงตามคะแนนแล้วดูจากบนลงล่าง จะเจอ ping ปกติก่อน
และเจอการสแกนเป็นอันดับสุดท้าย บนเครือข่ายนี้คะแนนของโมเดล**ไม่มีความหมาย**

## สาเหตุ: domain shift ไม่ใช่บั๊กของโมดูล 1

แยกสองอย่างนี้ออกจากกันสำคัญมาก จึงตรวจฟีเจอร์ที่สกัดได้โดยตรง:

| ตรวจ | ผล | แปลว่า |
|---|---|---|
| ฟีเจอร์ที่เป็น 0 ทั้งหมด | **0 / 46** | สกัดได้ครบทุกตัว ไม่มีคอลัมน์ตาย |
| ค่าไม่ finite (inf/nan) | **0** | ไม่มีบั๊กการหาร/ล้น |
| ค่า \|z\| สูงสุด | **18.5** | สุดโต่ง แต่อยู่ในระดับที่อธิบายได้ |

**โมดูล 1 ทำงานถูกต้อง** — สิ่งที่ผิดคือเครือข่ายนี้ไม่เหมือนสิ่งที่โมเดลเคยเห็น

ดูจากฟีเจอร์ที่เบี่ยงมากที่สุด จะเห็นว่าทุกตัวอธิบายได้ด้วยความต่างของเครือข่าย:

| ฟีเจอร์ | \|z\| เฉลี่ย | ทำไม |
|---|---|---|
| `PROTOCOL_1.0` | 2.82 (สูงสุด 18.5) | ICMP เป็นแค่ **0.29%** ของชุดฝึก แต่เราสร้าง ping เยอะ |
| `L7_PROTO` | 2.27 | frequency encoding คืนค่าต่ำมาก เพราะโปรโตคอลของ Mininet ไม่เคยอยู่ในชุดฝึก |
| `SRC_DISTINCT_DST_PORTS_LAST_W` | 2.50 | หน้าต่างพฤติกรรมยังเย็นอยู่ (เพิ่งเริ่มนับ) |
| `MIN_TTL` | 1.90 (คงที่) | Mininet ใช้ TTL เดียวกันหมด ต่างจากชุดข้อมูลที่หลากหลาย |
| `TCP_WIN_MAX_IN/OUT` | 3.10 / 2.45 | ขนาดหน้าต่าง TCP ของ Linux ใน VM ต่างจากอุปกรณ์ IoT จริง |

**IPv6 ยิ่งชัด** — `NF-ToN-IoT-v2` เป็นชุดข้อมูล IPv4 ล้วน ส่วน Mininet สร้าง ICMPv6 multicast
ตอนโฮสต์บูต โมเดลจึงไม่เคยเห็นอะไรแบบนี้เลย (345× threshold)

## สิ่งที่ผลนี้ยืนยัน

**ยืนยันข้อสรุปเรื่องการนำไปใช้จริงด้วยหลักฐานตรง ไม่ใช่การให้เหตุผล** —
[deployment-runbook.md](deployment-runbook.md) เขียนไว้ว่าต้องเทรนใหม่ทุกเครือข่าย
เพราะโมเดลเรียนรู้ว่า "ปกติ" ของเครือข่ายนั้นหน้าตาอย่างไร **การทดลองนี้แสดงให้เห็นว่าเกิดอะไรขึ้นถ้าไม่ทำ**

## ⚠️ สิ่งที่ผลนี้ไม่ได้ยืนยัน

- **ไม่ได้แปลว่าโมเดลใช้ไม่ได้** — บนชุดทดสอบของชุดข้อมูลเดียวกัน recall 87.59% ที่ FPR 4.97%
- **ไม่ได้วัดความแม่นยำ** — ทราฟฟิกทั้งหมดเราสร้างเอง ทั้งปกติและโจมตี ตัวเลขใด ๆ จากตรงนี้
  ไม่ใช่การประเมินความสามารถในการตรวจจับ **นี่คือการทดสอบการเชื่อมต่อของระบบ (integration test)**
- **ยังไม่ได้เทียบค่าฟีเจอร์กับ nProbe** — ทวนสอบได้ว่าโมดูล 1 ผลิตค่าที่สมเหตุสมผลและครบถ้วน
  แต่ยังไม่ได้พิสูจน์ว่าค่าตรงกับที่ nProbe จะให้บนแพ็กเก็ตชุดเดียวกัน

## ขั้นตอนทำซ้ำ

```bash
# ใน VM (ดู mininet-vm-setup.md สำหรับการติดตั้ง)
PYTHONPATH=$HOME/nids ~/ryu-venv/bin/ryu-manager --observe-links ryu.app.ofctl_rest \
  $HOME/nids/network_simulation/ryu_app.py &
sudo PYTHONPATH=$HOME/nids python3 network_simulation/topology.py    # มี mirror อัตโนมัติ

# ใน Mininet CLI
mininet> nids1 cd /home/ekkasit/nids && .venv/bin/python -m web.backend.live_capture \
           --source nids1-eth0 --processed-dir data/processed_w50 \
           --artifacts-dir artifacts/models/optuna-denoising-50 &
mininet> iot1 curl -s -o /dev/null http://10.0.2.11/
mininet> atk1 for p in 21 22 23 80; do timeout 1 bash -c "</dev/tcp/10.0.2.11/$p"; done
```

> ⚠️ ถ้าเขียนสคริปต์อัตโนมัติ **อย่าใช้ `host.cmd()` กับ process ที่ต้องรันค้าง** —
> `cmd()` รอจนคำสั่งจบ ใส่ `&` ก็ไม่ช่วย ต้องใช้ `host.popen()`
> และอย่าอ่าน `popen().stdout.read()` จนจบเพราะ process ลูกของ nfstream ถือ pipe ไว้ทำให้ค้าง

> การทดสอบการทำงานร่วมกันของทั้งระบบดำเนินการบนเครือข่ายจำลอง Mininet ที่มีสวิตช์ OpenFlow
> หนึ่งตัวควบคุมด้วย Ryu และมีโฮสต์เฝ้าระวังเชื่อมต่อผ่านพอร์ตสำเนาทราฟฟิก (SPAN port)
> ผลการทดสอบพบว่าโมดูลทั้งหกทำงานต่อเนื่องกันได้สมบูรณ์ โดยสกัดโฟลว์ได้ 56 รายการ
> จากทราฟฟิกจริงและบันทึกผลการตรวจจับลงฐานข้อมูลโดยไม่มีข้อผิดพลาด
> อย่างไรก็ตามแบบจำลองซึ่งฝึกด้วยชุดข้อมูล NF-ToN-IoT-v2 จัดให้โฟลว์ทั้งหมดเป็นความผิดปกติ
> เนื่องจากลักษณะทราฟฟิกของเครือข่ายจำลองแตกต่างจากชุดข้อมูลที่ใช้ฝึกอย่างสิ้นเชิง
> การตรวจสอบค่าคุณลักษณะที่สกัดได้ยืนยันว่าโมดูลสกัดโฟลว์ทำงานถูกต้อง
> (ไม่มีคุณลักษณะใดเป็นศูนย์ทั้งหมดและไม่มีค่าที่ไม่จำกัด) ความผิดพลาดจึงเกิดจากความแตกต่าง
> ของโดเมนข้อมูล ไม่ใช่ข้อบกพร่องของการสกัด ผลนี้สนับสนุนข้อสรุปว่าการนำระบบไปใช้กับเครือข่ายใหม่
> จำเป็นต้องฝึกแบบจำลองด้วยทราฟฟิกปกติของเครือข่ายนั้น
