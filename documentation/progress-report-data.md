### 4.1.1 คุณลักษณะเชิงพฤติกรรมที่พัฒนาขึ้นเอง

นอกจาก 43 คุณลักษณะจากชุดข้อมูลต้นฉบับ ได้เพิ่มอีก **3 คุณลักษณะ** ที่คำนวณจาก
พฤติกรรมข้ามโฟลว์ เพราะโฟลว์เดี่ยวๆ ของการสแกนแทบไม่ต่างจากการเชื่อมต่อสั้นปกติ
สิ่งที่ต่างคือ*จำนวนโฟลว์ที่พุ่งไปหลายปลายทางในเวลาสั้น*

| คุณลักษณะ | ความหมาย | ค่าเฉลี่ย | สูงสุด |
|---|---|---|---|
| `SRC_DISTINCT_DST_IPS_LAST_W` | ปลายทางที่ต่างกัน ใน 50 โฟลว์ล่าสุดของต้นทางนี้ | 6.15 | 50 |
| `SRC_DISTINCT_DST_PORTS_LAST_W` | พอร์ตปลายทางที่ต่างกัน ใน 50 โฟลว์ล่าสุด | 24.13 | 50 |
| `DST_DISTINCT_SRC_IPS_LAST_W` | ต้นทางที่ต่างกัน ที่ยิงมาปลายทางนี้ ใน 50 โฟลว์ล่าสุด | 1.84 | 50 |

**เหตุผลที่ใช้หน้าต่างแบบเลื่อน (bounded window) ไม่ใช่ค่ารวมทั้งชุดข้อมูล:**
ชุดข้อมูลนี้มีเครื่องในห้องทดลองเพียง ~10 เครื่องที่สร้าง traffic ถึง 94% ของทั้งหมด
และ*เครื่องเดียวกัน*สร้างทั้ง traffic ปกติและการโจมตี ถ้าใช้ค่ารวมต่อ IP ค่าจะเกือบคงที่
ต่อเครื่อง โมเดลจะเรียนรู้ว่า "นี่คือเครื่องไหน" แทนที่จะเรียนรู้พฤติกรรมการสแกน
และค่าของแถวปกติจะถูกปนเปื้อนจากแถวโจมตีของเครื่องเดียวกันที่ไปอยู่ในชุด val/test

จำนวนต้นทางที่พบ 23,079 IP ปลายทาง 6,868 IP

## 4.3 ผลการประเมินประสิทธิภาพของโมเดล

### 4.3.1 สถาปัตยกรรมโมเดลที่เลือก

ปรับจูนด้วย **Optuna (Tree-structured Parzen Estimator) จำนวน 50 trials**
โดยตั้งเป้าหมายการค้นหาเป็น **recall ที่ FPR ≤ 5%** ไม่ใช่ ROC-AUC

| พารามิเตอร์ | ค่า |
|---|---|
| จำนวนอินพุต | 46 |
| ชั้นซ่อน | [128] |
| ขนาดชั้นแฝง (latent) | 64 |
| noise_std (denoising) | 0.2167 |
| dropout | 0.0 |
| learning rate | 0.000405 |
| batch size | 256 |
| ROC-AUC บน validation | 0.9586 |

**ใช้ Denoising Autoencoder** คือเติมสัญญาณรบกวนแบบเกาส์เซียนเข้าที่อินพุตของ encoder
แต่คำนวณ loss เทียบกับข้อมูล*ต้นฉบับที่ไม่มีสัญญาณรบกวน* บังคับให้โมเดลเรียนรู้โครงสร้าง
ของข้อมูลปกติแทนการจำ ซึ่งจำเป็นเพราะสถาปัตยกรรมที่ได้เป็นแบบ overcomplete
(latent 64 > input 46) ที่ปกติจะลอกข้อมูลผ่านได้โดยไม่ต้องเรียนรู้อะไร

### 4.3.5 ผลเมื่อปรับสัดส่วนข้อมูลให้เหมือนเครือข่ายจริง

ชุดทดสอบมีการโจมตีถึง 86% เพราะถูกสร้างมาเพื่อ*วัดการตรวจจับ* ไม่ใช่เพื่อ*เหมือนเครือข่าย*
จึงทดสอบเพิ่มโดยสุ่มลดให้ข้อมูลปกติเป็น 95% (ไม่สร้างแถวใหม่ ตัดออกอย่างเดียว)

| สัดส่วน | Accuracy | Recall | Precision | FPR | Macro F1 |
|---|---|---|---|---|---|
| ชุดทดสอบเดิม (โจมตี 86%) | 0.8867 | 0.8759 | 0.9905 | 4.97% | 0.8187 |
| สมดุล 50/50 | 0.9130 | 0.8757 | 0.9462 | 4.97% | 0.9129 |
| **ปกติ 95% (สมจริง)** | 0.9466 | 0.8779 | **0.4815** | 4.97% | 0.7966 |

### 4.4.1 การสกัดคุณลักษณะจากทราฟฟิกจริง (โมดูลที่ 1)

จาก 43 คุณลักษณะในสคีมา NFStream ให้มาตรงๆ 16 ตัว, คำนวณต่อได้ 7 ตัว
ส่วนอีก **19 ตัวต้องเขียนโค้ดอ่านค่าจาก header ของแพ็กเก็ตดิบเอง** ได้แก่ TTL,
TCP window, การส่งซ้ำ, ฮิสโทแกรมขนาดแพ็กเก็ต, ICMP, DNS และ FTP
เพราะ NFStream ไม่ได้เปิดเผยค่าเหล่านี้

### 4.4.2 หน้าจอแดชบอร์ด

แบ่งเป็น 3 แท็บ

1. **Live** — แสดงโฟลว์ที่ไหลเข้ามาแบบทันที มีส่วนเน้นโฟลว์ล่าสุด (spotlight)
   พร้อมแถบเทียบค่าความคลาดเคลื่อนกับค่าขีดแบ่ง, ตารางโฟลว์ที่กรองได้,
   ปุ่มหยุดชั่วคราว และแผงอธิบายผล SHAP ด้านขวา
2. **Trend** — กราฟอัตราความผิดปกติตามเวลา เลือกช่วงได้ 8 ระดับ (5 นาที – 24 ชั่วโมง)
   ลากคลุมเพื่อเจาะดูโฟลว์ในช่วงนั้นได้ พร้อมสถิติแยกตามโปรโตคอล/ต้นทาง/พอร์ต
3. **Firewall gaps** — โฟลว์ที่โมเดลจับได้แต่ไฟร์วอลล์จะปล่อยผ่าน

**การออกแบบที่ตั้งใจ 2 อย่าง**

- **ช่วงที่ไม่มี traffic แสดงเป็นลายขวาง ไม่ใช่ 0%** — "ไม่มีข้อมูล" กับ "มีข้อมูลแต่ปกติทั้งหมด"
  เป็นคนละเรื่อง ถ้ารวมเป็นเส้นเดียวกัน เซ็นเซอร์ที่ตายจะดูเหมือนเครือข่ายที่สงบ
- **ไม่ใช้คำว่า "การโจมตี" กับสิ่งที่โมเดล flag** ใช้คำว่า "ผิดปกติ" เพราะระบบแยกได้แค่
  ปกติ/ไม่ปกติ ส่วนการตัดสินว่าเป็นการโจมตีหรือไม่เป็นหน้าที่ของคนโดยดูจาก SHAP

### 4.4.3 การอธิบายผลด้วย SHAP

เรียกเมื่อผู้ใช้ร้องขอเท่านั้น ใช้เวลา **~23 มิลลิวินาที ถึงไม่กี่วินาที** ต่อโฟลว์

แผงอธิบายผลแสดง

1. **การตรวจสอบคุณสมบัติ Local Accuracy** — `base_value + Σ SHAP = reconstruction error`
   ซึ่งตรวจสอบแล้วได้ค่าคลาดเคลื่อนเหลือ **0.000000** ตรงตามคุณสมบัติข้อที่ 1
   ที่ Lundberg & Lee (2017) ระบุไว้ (อ้างในบทที่ 2 หัวข้อ 2.1.4)
2. **คุณลักษณะที่มีอิทธิพลสูงสุด** เรียงตามขนาดอิทธิพล แท่งขวาของแกนกลาง =
   ดันให้ค่าความคลาดเคลื่อนสูงขึ้น แท่งซ้าย = ดึงลง
3. **ค่าจริงของคุณลักษณะพร้อมหน่วย** — ระบบเก็บค่าที่ปรับมาตรฐานแล้ว (z-score)
   จึงย้อนกลับด้วยค่าเฉลี่ยและส่วนเบี่ยงเบนมาตรฐานของชุดฝึก เพื่อแสดงค่าจริง
   เช่น `2,929 B`, `34.0 hosts`, `320,000 bit/s` ตรวจสอบความถูกต้องของการย้อนกลับแล้ว
   ได้ค่าคลาดเคลื่อนระดับ 1e-15 (เท่ากับความละเอียดของเลขทศนิยม)

## 4.5 อภิปรายผลการทดลอง

**1. โมเดลตรวจจับได้ดีมากในการโจมตีที่มีร่องรอยชัดในระดับโฟลว์**
backdoor 99.92%, ransomware 99.71%, password 99.10%, ddos 98.88% — ทั้งหมดนี้
มีลักษณะที่เห็นได้จากข้อมูลสรุประดับโฟลว์ เช่น การเชื่อมต่อค้างยาวผิดปกติ
การถ่ายโอนข้อมูลปริมาณมาก หรือการเชื่อมต่อซ้ำๆ ไปยังบริการเดียว

**2. คลาสที่ตรวจจับได้แย่ที่สุดสอดคล้องกับข้อจำกัดที่ระบุไว้ตั้งแต่ต้น**
xss ได้เพียง 74.04% ซึ่ง**ตรงกับข้อจำกัดข้อ 1.3.2 ข้อ 2** ที่เขียนไว้ว่าระบบไม่สามารถ
ตรวจจับการโจมตีที่อยู่ในเนื้อหาของแพ็กเก็ตได้ เพราะ XSS และ injection ซ่อนอยู่ใน
payload ของ HTTP ซึ่ง NetFlow ไม่ได้บันทึกเนื้อหาไว้เลย ผลการทดลองจึงเป็นการ
**ยืนยันข้อจำกัดที่คาดการณ์ไว้ล่วงหน้า** ไม่ใช่ความล้มเหลวที่ไม่ได้ตั้งใจ

**3. บรรลุเป้าหมาย FPR ที่ตั้งไว้**
FPR 4.97% อยู่ใต้เพดาน 5% ที่กำหนดไว้ ต่างจากเวอร์ชันก่อนหน้าที่มี FPR ประมาณ 29%

**4. คุณลักษณะเชิงพฤติกรรมที่พัฒนาขึ้นเองมีผลอย่างมีนัยสำคัญ**
พัฒนาการของ recall ที่ FPR ≈ 5% ตลอดโครงงาน

| ขั้นตอน | Recall | Macro F1 |
|---|---|---|
| โมเดลพื้นฐาน | 29.60% | 0.382 |
| + คุณลักษณะเชิงพฤติกรรม 3 ตัว | 45.87% | – |
| + Denoising Autoencoder | 59.50% | – |
| + ปรับจูนด้วย Optuna 50 trials (เป้าหมาย recall@FPR) | **87.59%** | **0.819** |

จุดเปลี่ยนสำคัญคือการ**เปลี่ยนเป้าหมายการค้นหาพารามิเตอร์จาก ROC-AUC เป็น
recall ที่ FPR ≤ 5%** เพราะสองค่านี้จัดอันดับโมเดลสวนทางกันได้ โมเดลที่มี AUC สูงกว่า
อาจให้ recall ที่จุดทำงานจริงต่ำกว่า

**5. ข้อจำกัดของชุดข้อมูลที่ตรวจพบและวัดผลได้**

- UDP ในชุดข้อมูลนี้ 95% เป็น DNS และ 78.3% ถูกติดป้ายว่าเป็นการโจมตี
- คลาส `xss` มี 51% ที่เป็นทราฟฟิก DNS ซึ่งเกิดจากการติดป้ายระดับ session
  (ทุกโฟลว์ในช่วงเวลาที่โจมตีได้ป้ายเดียวกันหมด รวมทั้งการค้นหาชื่อโดเมนปกติ)
- **ถ้าตัด UDP ออกทั้งหมดแล้ววัดใหม่ที่ค่าขีดแบ่งเดิม: recall 94.10%, FPR 4.81%, Macro F1 0.9025**

หมายความว่า **ค่า FPR 4.97% ที่รายงานเป็นขอบเขตบน** เพราะการแจ้งเตือนผิดบางส่วน
คือโมเดลตรวจพบทราฟฟิกปกติที่ถูกติดป้ายผิดเป็นการโจมตี

# บทที่ 5 สรุปผลการดำเนินงาน

## 5.1 ผลสรุปการดำเนินการ

**5.1.1 พัฒนาระบบตรวจจับครบทั้ง 6 โมดูล** ตั้งแต่การสกัดโฟลว์จากทราฟฟิกจริงด้วย
NFStream การเตรียมข้อมูล การตรวจจับด้วย Denoising Autoencoder การอธิบายผลด้วย
Kernel SHAP แดชบอร์ด และการตรวจสอบความครอบคลุมของไฟร์วอลล์
ได้ผลบนชุดทดสอบ 6.3 ล้านรายการที่ **recall 87.59% · FPR 4.97% · precision 99.05%**

**5.1.2 บูรณาการ XAI เข้ากับการตรวจจับแบบไม่มีผู้สอนได้จริง**
ซึ่งเป็นช่องว่างงานวิจัยที่ระบุไว้ในบทที่ 2 หัวข้อ 2.2.3 โดยตรวจสอบคุณสมบัติ
Local Accuracy ได้ค่าคลาดเคลื่อน 0.000000 และแสดงค่าคุณลักษณะในหน่วยจริง

**5.1.3 พัฒนาคุณลักษณะเชิงพฤติกรรม 3 ตัวที่ออกแบบเอง** เพื่อจับรูปแบบข้ามโฟลว์
ซึ่งเป็นสิ่งที่โฟลว์เดี่ยวๆ มองไม่เห็น และเป็นปัจจัยที่ทำให้ recall เพิ่มจาก 29.60% เป็น 45.87%

**5.1.4 ตรวจสอบคุณภาพระบบด้วยชุดทดสอบอัตโนมัติ 199 test cases**
ซึ่งพบข้อผิดพลาดที่มีผลรุนแรงหลายจุดในระหว่างการพัฒนา (ดูหัวข้อ 5.2)

## 5.2 ปัญหาและอุปสรรคที่พบ

**5.2.1 ความไม่ตรงกันระหว่างข้อมูลตอนฝึกกับตอนใช้งานจริง (train/serve skew)**
เป็นปัญหาที่ใหญ่ที่สุดของโครงงาน เพราะ**ไม่แสดงอาการเป็นข้อผิดพลาด** — ทุกค่าอยู่ใน
คอลัมน์ที่ถูก ชนิดข้อมูลถูก และขนาดดูสมเหตุสมผล แต่ความหมายผิด ตัวอย่างที่พบ

- NFStream นับจำนวนไบต์ที่ชั้น Ethernet แต่ชุดข้อมูลต้นฉบับนับที่ชั้น IP ทำให้
  ค่าเกินไป 14 ไบต์ต่อแพ็กเก็ต ใน 10 คอลัมน์พร้อมกัน — **ทดลองแล้วพบว่าจะทำให้
  FPR พุ่งจาก 4.97% เป็น 96.43%** คือระบบจะแจ้งเตือนแทบทุกโฟลว์
- คอลัมน์ `*_SECOND_BYTES` และ `*_AVG_THROUGHPUT` ไม่ใช่ค่าอัตราตามชื่อ
  เพราะ `FLOW_DURATION_MILLISECONDS` เป็น 0 ถึง 98.4% ของโฟลว์ทั้งหมด
  การคำนวณเป็นอัตราตามชื่อคอลัมน์ตรงกับข้อมูลจริง 0.00%

**5.2.2 การเลือกตัวชี้วัดสำหรับปรับจูนพารามิเตอร์**
การใช้ ROC-AUC เป็นเป้าหมายทำให้ได้โมเดลที่มี recall ที่จุดทำงานจริงต่ำ เนื่องจาก
ROC-AUC วัดทั้งเส้นโค้ง แต่ระบบใช้งานที่จุดเดียวคือ FPR ≤ 5%

**5.2.3 ข้อจำกัดของชุดข้อมูลที่ทำให้ตัวเลขไม่สะท้อนความจริงทั้งหมด**
การติดป้ายระดับ session ทำให้ทราฟฟิกปกติในช่วงเวลาที่โจมตีได้ป้ายว่าเป็นการโจมตีด้วย
และห้องทดลองมีเพียง ~10 เครื่องสร้าง traffic 94% ของทั้งหมด

**5.2.4 การจำลองเครือข่ายยังไม่ได้ทดสอบจริง**
Mininet ต้องใช้สิทธิ์ root และแพ็กเกจระดับระบบ ส่วน Ryu ยังไม่รองรับ Python เวอร์ชัน
ที่ใช้พัฒนา จึงเขียนโค้ดไว้แล้วแต่ยังไม่ได้รันจริง ทดสอบเฉพาะส่วนที่เชื่อมกับโมดูลที่ 6

## 5.3 ข้อเสนอแนะในการพัฒนาต่อไป

**5.3.1 ปรับค่าขีดแบ่งใหม่เมื่อนำไปใช้กับทราฟฟิกจริง** ค่าขีดแบ่งเป็นเปอร์เซ็นไทล์ของ
การกระจายค่าความคลาดเคลื่อน จึงใช้ได้เฉพาะกับการกระจายที่มันถูกคำนวณมา
การทดลองพบว่าความไม่ตรงกันของ `L7_PROTO` ทำให้ FPR ขยับเป็น 5.44% ซึ่งเกินเพดาน
แต่หากปรับค่าขีดแบ่งใหม่บนชุด validation จะกลับมาที่ 4.99% โดยแลกกับ recall 1.66 จุด

**5.3.2 ทดสอบบน Mininet + Ryu จริง** เพื่อวัดความเร็วในการตรวจจับและความเสถียร
เมื่อประมวลผลข้อมูลปริมาณมาก ตามที่ระบุไว้ในหัวข้อ 3.1.7 ข้อ 4

**5.3.3 ทดสอบกับชุดข้อมูลอื่นเพื่อยืนยันว่าไม่ได้ยึดติดกับชุดข้อมูลเดียว**
เนื่องจากพบว่า NF-ToN-IoT-v2 มีข้อจำกัดหลายอย่าง การทดสอบกับ CIC-IDS2017
หรือ UNSW-NB15 จะช่วยยืนยันว่าผลลัพธ์ไม่ได้มาจากลักษณะเฉพาะของชุดข้อมูล

**5.3.4 พัฒนาให้เรียนรู้พฤติกรรมปกติที่เปลี่ยนไปตามเวลาได้**
ตามข้อจำกัดข้อ 1.3.2 ข้อ 3 ที่ระบุว่าหากพฤติกรรมปกติของเครือข่ายเปลี่ยนไป
โมเดลอาจแจ้งเตือนผิดพลาด
