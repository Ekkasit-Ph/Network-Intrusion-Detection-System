# Prompt สำหรับวาดแผนภาพสถาปัตยกรรมระบบใหม่ (รูปภาพที่ 1)

คัดลอกข้อความในกรอบด้านล่างทั้งหมดไปวางใน Claude Design

> **สำคัญ:** รูปเดิมในเล่มวาดผิดมากกว่าแค่ชื่อฐานข้อมูล — เดิมวาดให้ NFStreamer ส่ง
> flow features เข้า FastAPI แล้ว FastAPI กระจายต่อ แต่ระบบจริง **ตัวเก็บข้อมูลเขียนลง
> ฐานข้อมูลโดยตรง** ส่วน FastAPI ทำหน้าที่อ่านเป็นหลัก prompt นี้แก้ให้ตรงแล้ว

---

## ข้อความ prompt

```
วาดแผนภาพสถาปัตยกรรมระบบ (System Architecture Diagram) สำหรับรายงานโครงงาน
ปริญญาตรีภาษาไทย เรื่อง "ระบบตรวจจับการบุกรุกเครือข่ายโดยใช้ออโตเอนโค้ดเดอร์และ
ปัญญาประดิษฐ์ที่อธิบายได้"

## บริบทการใช้งาน
- เป็นรูปประกอบในเล่มรายงานวิชาการ จะถูกพิมพ์ลงกระดาษ A4 ขนาดประมาณ 16 x 10 ซม.
- ต้องอ่านออกเมื่อพิมพ์ขาวดำ จึงห้ามใช้สีเป็นตัวแยกความหมายเพียงอย่างเดียว
  ให้ใช้เส้นทึบ/เส้นประ และรูปทรงกล่องช่วยแยกด้วย
- ป้ายกำกับใช้ภาษาไทยเป็นหลัก ตามด้วยศัพท์เทคนิคภาษาอังกฤษในวงเล็บ
  เช่น "ตรวจจับความผิดปกติ (Autoencoder Inference)"
- สไตล์เรียบ เป็นทางการ ไม่ต้องมีไอคอนตกแต่ง ไม่ต้องมีเงา ไม่ต้องมีไล่สี

## หัวใจของแผนภาพที่ต้องสื่อให้ถูก
ระบบนี้มี "กระบวนการที่เขียนข้อมูล" 3 ตัวที่ทำงานแยกกันเป็นอิสระ และมี "ตัวอ่านข้อมูล"
1 ตัว โดยใช้ฐานข้อมูล SQLite เป็นจุดเชื่อมต่อกลาง (integration point)
**กระบวนการเก็บข้อมูลไม่ได้ส่งผ่าน API แต่เขียนลงฐานข้อมูลโดยตรง**

## โครงสร้างที่ต้องวาด — แบ่งเป็น 4 กลุ่ม (วาดเป็นกรอบเส้นประครอบแต่ละกลุ่ม)

### กลุ่ม A: แหล่งข้อมูลนำเข้า (Data Sources)  — วางซ้ายสุด
กล่อง A1: "เครือข่ายอุปกรณ์ IoT จำลอง (Mininet + Ryu SDN Controller)"
กล่อง A2: "ชุดข้อมูล NF-ToN-IoT-v2 (สำหรับสาธิตแบบมีเฉลย)"

หมายเหตุใต้กลุ่ม: "เลือกใช้ทางใดทางหนึ่ง"

### กลุ่ม B: กระบวนการตรวจจับ (Detection Pipeline) — วางกลางซ้าย เรียงลงล่าง
เป็นสายโซ่ต่อกันแนวตั้ง 3 กล่อง มีลูกศรชี้ลงระหว่างกัน:

กล่อง B1: "โมดูล 1 — สกัดคุณลักษณะโฟลว์ (NFStream + NFPlugin)"
   ป้ายกำกับใต้กล่อง: "43 คุณลักษณะดิบ ตามมาตรฐาน NetFlow v9"

กล่อง B2: "โมดูล 2 — เตรียมข้อมูลแบบทันที (Online Preprocessing)"
   ป้ายกำกับใต้กล่อง: "คุณลักษณะเชิงพฤติกรรม 3 รายการ + เข้ารหัสหมวดหมู่ +
   log1p + กำหนดมาตรฐาน → 46 คุณลักษณะ"

กล่อง B3: "โมดูล 3 — ตรวจจับความผิดปกติ (Denoising Autoencoder)"
   ป้ายกำกับใต้กล่อง: "ค่าความคลาดเคลื่อน เทียบกับค่าขีดแบ่ง τ = 0.001944"

ลูกศรจาก A1 เข้า B1 (เส้นทึบ) กำกับว่า "ทราฟฟิกจริง"
ลูกศรจาก A2 เข้า B3 โดยตรง (เส้นประ) กำกับว่า "โหมดสาธิต — ข้อมูลผ่านการเตรียมแล้ว"

### กลุ่ม C: จัดเก็บข้อมูล (Storage) — วางกลางขวา
กล่องทรงกระบอก (สัญลักษณ์ฐานข้อมูล) ชื่อ "ฐานข้อมูล SQLite"
ภายในหรือใต้กระบอก ระบุ 4 ตาราง:
   - flows (ผลการตรวจจับ)
   - replay_ground_truth (เฉลยสำหรับโหมดสาธิต)
   - explanations (ผลการอธิบายด้วย SHAP)
   - firewall_checks (ผลตรวจสอบไฟร์วอลล์)

ลูกศรจาก B3 เข้ากระบอก **เส้นทึบหนา** กำกับว่า "เขียนโดยตรง (ไม่ผ่าน API)"
— จุดนี้สำคัญ ขอให้เน้นให้เห็นชัด

### กลุ่ม D: บริการและการแสดงผล (Services & Presentation) — วางขวาสุด
กล่อง D1: "FastAPI Backend"
   ป้ายกำกับใต้กล่อง: "/alerts · /stats · /stats/trend · /flow · /meta · /firewall-gaps"

กล่อง D2: "โมดูล 4 — บริการอธิบายผล (Kernel SHAP)"
   ป้ายกำกับใต้กล่อง: "เรียกตามคำขอเท่านั้น ใช้เวลา ~23 มิลลิวินาที ถึงไม่กี่วินาที"

กล่อง D3: "โมดูล 5 — แดชบอร์ด (HTML/CSS/JavaScript)"
   ป้ายกำกับใต้กล่อง: "เรียกดูข้อมูลเป็นรอบทุก 2 วินาที (HTTP polling)"

ลูกศรสองทิศระหว่าง D1 กับกระบอก SQLite กำกับว่า "อ่าน"
ลูกศรจาก D3 ไป D1 กำกับว่า "polling ทุก 2 วินาที"
ลูกศรจาก D3 ไป D2 (ผ่าน D1) กำกับว่า "POST /explain — เมื่อผู้ใช้ร้องขอ"
ลูกศรจาก D2 กลับเข้ากระบอก กำกับว่า "บันทึกผลอธิบาย"

### กลุ่ม E: ตรวจสอบไฟร์วอลล์ (แยกออกมา วางล่างสุด)
กล่อง E1: "กฎไฟร์วอลล์ (Ryu flow table / iptables)"
กล่อง E2: "โมดูล 6 — เปรียบเทียบผลตรวจจับกับกฎไฟร์วอลล์"
   ป้ายกำกับใต้กล่อง: "อ่านอย่างเดียว ไม่แก้ไขกฎ"

ลูกศรจาก E1 เข้า E2 กำกับว่า "อ่านกฎ"
ลูกศรจากกระบอก SQLite เข้า E2 กำกับว่า "อ่านโฟลว์ที่ผิดปกติ"
ลูกศรจาก E2 กลับเข้ากระบอก กำกับว่า "เขียน firewall_checks"

## สิ่งที่ห้ามใส่เด็ดขาด (รูปเดิมมีแต่ผิด)
- ห้ามใส่ PostgreSQL — ระบบใช้ SQLite
- ห้ามใส่ SSE Stream หรือ Server-Sent Events — ระบบใช้ HTTP polling
- ห้ามวาดลูกศรจากโมดูลสกัดโฟลว์เข้า FastAPI — กระบวนการตรวจจับเขียนฐานข้อมูลโดยตรง
- ห้ามใส่ React

## การจัดวาง
ไหลจากซ้ายไปขวา: แหล่งข้อมูล → กระบวนการตรวจจับ → ฐานข้อมูล → บริการและแสดงผล
โดยมีกลุ่มตรวจสอบไฟร์วอลล์แยกอยู่ด้านล่าง เชื่อมกลับเข้าฐานข้อมูล
ให้กล่องมีขนาดใกล้เคียงกัน เส้นลูกศรไม่ตัดกัน และเว้นช่องว่างให้อ่านป้ายกำกับได้สบาย

## ผลลัพธ์ที่ต้องการ
รูปเดียว พื้นหลังขาว เหมาะกับการวางในเอกสาร Word
```

## ข้อมูลอ้างอิงเพิ่มเติม เผื่อ Claude Design ถามกลับ

| ประเด็น | คำตอบ |
|---|---|
| ทำไมกระบวนการตรวจจับไม่ส่งผ่าน API | เพราะ `live_capture.py` เป็นโปรเซสแยกที่รวมทั้งการสกัดโฟลว์ เตรียมข้อมูล และตรวจจับไว้ด้วยกัน แล้วเขียนผลลง SQLite โดยตรง การส่งผ่าน HTTP จะเพิ่มชั้นที่ไม่จำเป็นระหว่างโปรเซสที่อยู่บนเครื่องเดียวกัน |
| ใครเขียนลงฐานข้อมูลบ้าง | 3 ตัว: `live_capture.py` (ตาราง flows), `replay_demo.py` (flows + replay_ground_truth), `ryu_log_compare.py` (firewall_checks) และ FastAPI เขียนเฉพาะ explanations เมื่อผู้ใช้กดขอคำอธิบาย |
| FastAPI ทำอะไรบ้าง | อ่านข้อมูลจาก SQLite ให้แดชบอร์ด (6 endpoint) และเป็นทางเข้าเดียวที่มีการเขียน คือ `POST /explain/{flow_id}` ซึ่งคำนวณ SHAP แล้วบันทึกผลไว้ |
| ทำไมโหมดสาธิตเข้า B3 โดยตรง | `replay_demo.py` ใช้ข้อมูลจากชุดทดสอบที่ผ่านการเตรียมข้อมูลแบบกลุ่มมาแล้ว จึงข้ามโมดูล 1 และ 2 ไปเข้าการให้คะแนนเลย |
| ตาราง replay_ground_truth มีไว้ทำไม | เก็บเฉลยของโฟลว์ในโหมดสาธิต เพื่อให้ตรวจสอบได้ว่าโมเดลตัดสินถูกหรือผิด ทราฟฟิกจริงไม่มีเฉลย ตารางนี้จึงว่างเสมอในการใช้งานจริง |

## สิ่งที่ต้องแก้ในเล่มให้สอดคล้องกับรูปใหม่

รูปใหม่จะขัดกับข้อความในหัวข้อ 3.1.5 ที่ยังเขียนตามรูปเดิม จึงต้องแก้ข้อความด้วย
โดยใช้ข้อความในไฟล์ `report-corrections.md` ส่วนที่ 1.4 และเพิ่มย่อหน้านี้:

> ข้อสังเกตสำคัญของสถาปัตยกรรมนี้คือ **กระบวนการตรวจจับเขียนผลลงฐานข้อมูลโดยตรง
> โดยไม่ผ่าน API** เนื่องจากโมดูลที่ 1 ถึง 3 ทำงานรวมกันเป็นโปรเซสเดียวบนเครื่องเดียวกับ
> ฐานข้อมูล การส่งข้อมูลผ่าน HTTP ระหว่างกันจะเพิ่มชั้นการทำงานที่ไม่จำเป็น ส่วน FastAPI
> ทำหน้าที่เป็นตัวอ่านข้อมูลให้แดชบอร์ดเป็นหลัก และเป็นทางเข้าเดียวที่มีการเขียนข้อมูล
> คือเมื่อผู้ดูแลระบบร้องขอคำอธิบายด้วย SHAP ฐานข้อมูล SQLite จึงทำหน้าที่เป็นจุดเชื่อมต่อ
> กลาง (integration point) ระหว่างกระบวนการที่ทำงานแยกกัน 3 กระบวนการ ได้แก่
> การตรวจจับ การสาธิตด้วยข้อมูลที่มีเฉลย และการตรวจสอบไฟร์วอลล์
