# การทดลอง: threshold แยกตามโปรโตคอล — **ผลเป็นลบ ไม่ควรนำไปใช้**

รันด้วย `python -m scripts.protocol_thresholds` · ผลดิบ: [`artifacts/protocol-thresholds.json`](../../artifacts/protocol-thresholds.json)

## สมมติฐานตั้งต้น (ซึ่งผิด)

จากการวัดในเอกสารก่อนหน้า โมเดลถูกปรับเทียบ (calibrate) ไม่เหมือนกันระหว่าง TCP กับ UDP —
ที่ threshold เดียวกัน benign TCP โดน flag 4.65% แต่ benign UDP โดน 6.69%

จึงตั้งสมมติฐานว่า **UDP ใช้งบ false positive เกินส่วน** ถ้าแยก threshold แล้วรัด UDP ให้อยู่ที่ 5%
น่าจะคืนงบมาให้ TCP และได้ recall รวมสูงขึ้น

**สมมติฐานนี้ผิด และผิดในทิศทางตรงกันข้าม**

## วิธีทดลอง

สามนโยบาย **fit บน validation ทั้งหมด แล้วนำไปใช้กับ test โดยไม่แก้ไข** ตามข้อจำกัดของโครงงาน

| นโยบาย | วิธีเลือก threshold |
|---|---|
| `global` | ค่าเดียว ที่เปอร์เซ็นไทล์ 95 ของ benign ทั้งหมด — **นโยบายที่ใช้อยู่** |
| `equal-fpr` | แต่ละโปรโตคอลตัดที่เปอร์เซ็นไทล์ 95 ของ benign ตัวเอง |
| `budgeted` | แบ่งงบ FPR 5% ข้ามโปรโตคอลเพื่อให้ recall รวมสูงสุด (Lagrangian + greedy top-up) |

## ผลบนชุดทดสอบ

| นโยบาย | recall | FPR | precision | FPR ของ TCP | FPR ของ UDP |
|---|---|---|---|---|---|
| **`global` (ใช้อยู่)** | **87.59%** | 4.97% | 99.05% | 4.65% | 6.69% |
| `equal-fpr` | 86.36% | 4.96% | 99.04% | 4.98% | 4.81% |
| `budgeted` | **87.72%** | 4.97% | 99.05% | 4.73% | **7.64%** |

## ข้อสรุปสามข้อ

### 1. `equal-fpr` ซึ่งเป็นวิธีที่ "ดูสมเหตุสมผล" ทำให้แย่ลงชัดเจน

recall ลดลง 1.23 จุด โดย FPR เท่าเดิม และ**ทำลายสองคลาสที่อยู่บน UDP**:
dos ร่วงจาก 80.81% เหลือ **61.87%** (−18.9 จุด) · mitm ร่วงจาก 78.97% เหลือ **65.42%** (−13.6 จุด)

เพราะการรัด UDP ให้เหลือ FPR 5% ไปตัดเอา flow ของ dos ที่นั่งอยู่เหนือเส้นเดิมเพียงเล็กน้อยออกไปพอดี
(ดู [dataset-limitations.md](dataset-limitations.md) — dos มี error มัธยฐานแค่ 1.35 เท่าของ threshold)

### 2. การแบ่งงบที่เหมาะที่สุด ให้ UDP **มากขึ้น** ไม่ใช่น้อยลง

`budgeted` เลือกให้ UDP มี FPR **7.64%** ซึ่งสูงกว่า `global` ที่ 6.69% เสียอีก
แปลว่า **false positive ที่เกิดบน UDP "คุ้ม" กว่าบน TCP** — มันซื้อการตรวจจับที่ถูกต้องได้มากกว่าต่อหนึ่งหน่วย

สมมติฐานตั้งต้นที่ว่า "UDP ใช้งบเกินส่วน" จึงกลับหัว งบที่ UDP ใช้อยู่ **ยังน้อยเกินไปด้วยซ้ำ**

### 3. แม้เป็นวิธีที่ดีที่สุด ก็ได้มาแค่ +0.13 จุด — ไม่คุ้มความซับซ้อน

`budgeted` ได้ 87.72% เทียบ 87.59% = **+0.13 จุด** ที่ FPR เท่ากัน

แลกกับ: artifact ของ threshold ซับซ้อนขึ้น (3 ค่าแทน 1) · ต้องปรับเทียบแยกรายโปรโตคอลตอน deploy ·
ต้องรู้โปรโตคอลก่อนตัดสิน · และถ้าเครือข่ายปลายทางมีสัดส่วนโปรโตคอลต่างจากชุดฝึก การแบ่งงบนี้จะไม่ใช่ค่าที่เหมาะอีกต่อไป

**ข้อเสนอ: คงใช้ threshold เดียวต่อไป**

## บันทึกความผิดพลาดระหว่างทดลอง

รอบแรก `budgeted` ใช้งบ FPR แค่ **3.75% จาก 5%** ที่ให้ได้ แล้วได้ recall 86.45% ซึ่งต่ำกว่า `global`
ถ้ารายงานตามนั้นจะเป็นการเทียบ "นโยบายที่ใช้งบครึ่งเดียว" กับ "นโยบายที่ใช้งบเต็ม" แล้วสรุปว่าแพ้

สาเหตุคือการทำ bisection บน Lagrangian multiplier อย่างเดียวไม่พอ — จุด argmax กระโดดข้าม grid
ค่า λ แรกที่ทำให้อยู่ในงบจึงอาจอยู่ในงบแบบเหลือเฟือ แก้ด้วยการเพิ่มความละเอียด grid
จาก 400 เป็น 4,000 และเติม **greedy top-up** ซื้องบที่เหลือทีละขั้น
โดยเลือกโปรโตคอลที่ให้การตรวจจับต่อ false positive สูงสุดเสมอ

หลังแก้ `budgeted` ใช้งบครบ 4.97% และกลายเป็นชนะ `global` เล็กน้อยแทนที่จะแพ้
**ข้อสรุปเปลี่ยนจาก "แย่กว่า" เป็น "ดีกว่านิดเดียว ไม่คุ้ม" ซึ่งคนละเรื่องกัน**

## สิ่งที่ใช้ตอบกรรมการได้

> งานนี้ทดลองใช้ค่าขีดแบ่งแยกตามโปรโตคอล เนื่องจากพบว่าแบบจำลองมีการปรับเทียบต่างกัน
> ระหว่าง TCP และ UDP ผลการทดลองบนชุดทดสอบพบว่าการกำหนดอัตราผลบวกลวงให้เท่ากัน
> ทุกโปรโตคอลทำให้ recall ลดลง 1.23 จุด และลดอัตราการตรวจจับคลาส dos ลงถึง 18.9 จุด
> ส่วนการจัดสรรงบประมาณผลบวกลวงแบบเหมาะที่สุดให้ผลดีขึ้นเพียง 0.13 จุด ซึ่งไม่คุ้มกับ
> ความซับซ้อนที่เพิ่มขึ้น จึงคงใช้ค่าขีดแบ่งเดียวตามเดิม การทดลองนี้ยังแสดงว่าผลบวกลวง
> ที่เกิดบนทราฟฟิก UDP ให้ผลตอบแทนเป็นการตรวจจับที่ถูกต้องสูงกว่าบน TCP ซึ่งตรงข้ามกับ
> สมมติฐานตั้งต้น
