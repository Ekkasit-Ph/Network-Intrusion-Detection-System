# ผลการวัดทรัพยากร (resource usage)

ปิดแทร็กที่ 3 จาก 4 ที่ `PROJECT.md` สัปดาห์ 13–15 สัญญาไว้
รันด้วย `python -m scripts.benchmark --suite` · ผลดิบอยู่ที่ [`artifacts/benchmark.json`](../artifacts/benchmark.json)

## เครื่องที่วัด

```
Intel Core i5-11320H @ 3.20GHz · 4 cores / 8 threads · RAM 15.4 GB
NVIDIA GeForce GTX 1650 4GB · torch 2.13.0 · Pop!_OS 24.04 (Linux 7.0.11)
```

> ⚠️ ตัวเลข throughput ที่ไม่ระบุเครื่องไม่มีความหมาย ต้องอ้างสเปกนี้ทุกครั้งที่อ้างผล
> **นี่คือโน้ตบุ๊ก ไม่ใช่เซิร์ฟเวอร์** — ถ้าระบบทำงานทันบนเครื่องระดับนี้ เป็นข้ออ้างที่หนักแน่นกว่า

## สี่ข้อสรุป

### 1. คอขวดอยู่ที่การสกัดโฟลว์ ไม่ใช่โมเดล — ห่างกัน 240 เท่า

```
สกัดโฟลว์ (NFStream + nDPI)    8,796 flow/s   ← คอขวด
เตรียมข้อมูล                  20,385 flow/s
ให้คะแนน (autoencoder)     2,131,340 flow/s
```

การเร่งโมเดลให้เร็วขึ้นไม่มีประโยชน์เลย ระบบจะยังติดอยู่ที่ 8,796 flow/s อยู่ดี
**ถ้าจะปรับปรุงสมรรถนะในอนาคต ต้องไปที่โมดูล 1** เช่นเพิ่ม `n_meters` ของ NFStreamer

### 2. GPU ทำให้ latency ต่อโฟลว์ **แย่ลง** 2 เท่า

| | CPU | GPU |
|---|---|---|
| ให้คะแนน 1 โฟลว์ | **0.067 ms** | 0.136 ms |
| ให้คะแนนเป็นชุด | 2.1M/s | 5.0M/s |
| RAM โมเดล | **3.1 MB** | 90.8 MB |

โมเดลมีแค่ 28,526 พารามิเตอร์ (115 KB) **ต้นทุนการส่งข้อมูลไป-กลับ GPU สูงกว่าการคำนวณเอง**
GPU ชนะเฉพาะตอนประมวลผลเป็นชุดใหญ่ ซึ่งไม่ใช่รูปแบบการใช้งานจริงของ IDS ที่โฟลว์ทยอยเข้ามาทีละตัว

→ **ยืนยันว่าการที่ `Dockerfile` เลือก PyTorch แบบ CPU-only เป็นการตัดสินใจที่ถูก** ไม่ใช่ข้อจำกัด

### 3. 1 core ก็พอสำหรับเครือข่ายขนาดเล็ก-กลาง

บีบเหลือ core เดียวยังสกัดได้ 4,460 flow/s และให้คะแนนได้ 1.34 ล้าน flow/s
ใช้ RAM สำหรับโมเดลแค่ 3 MB

**สิ่งที่เคลมได้:** "ทำงานได้ที่ 4,460 flow/s บน i5-11320H 1 core"
**สิ่งที่เคลมไม่ได้:** "ทำงานบน Raspberry Pi ได้" — ยังไม่ได้ทดสอบ อย่าคาดคะเนข้ามฮาร์ดแวร์

### 4. SHAP 8.7 ms ตรงตามข้อจำกัดที่ตั้งไว้

`PROJECT.md` กำหนดว่า SHAP ต้องเป็น on-demand ห้ามรันทุกโฟลว์ ตัวเลขยืนยันว่าถูกต้อง:

```
ให้คะแนน 1 โฟลว์   0.067 ms
SHAP 1 โฟลว์       8.716 ms   ← ช้ากว่า 130 เท่า
```

ถ้ารัน SHAP ทุกโฟลว์ ระบบจะรองรับได้แค่ ~115 flow/s แทนที่จะเป็น 8,796

## บั๊กที่เจอระหว่างทำ benchmark นี้

**`nfstream` หด CPU affinity ของ process จาก 8 เหลือ 2 อย่างถาวร และไม่คืนให้**
([`nfstream/utils.py::set_affinity`](../.venv/lib/python3.12/site-packages/nfstream/utils.py) เรียกจาก `streamer.py:536`)

meter ของ nfstream รันใน process แยกอยู่แล้ว การบีบนี้จึงไปโดนแต่**ทุกอย่างที่อยู่ถัดจากตัวสกัด**
— การ scale, การให้คะแนน, SHAP — ซึ่งใน [`live_capture.py`](../web/backend/live_capture.py) อยู่ใน process เดียวกันทั้งหมด

**ผลกระทบที่วัดได้:**

| | ก่อนแก้ | หลังแก้ |
|---|---|---|
| ให้คะแนนเป็นชุด | 10,220 flow/s | **2,275,190 flow/s** (222 เท่า) |
| SHAP | 90.1 ms | **9.4 ms** (10 เท่า) |

สาเหตุที่รุนแรงขนาดนี้: torch ตั้ง thread pool ไว้ 4 threads แต่เหลือ CPU แค่ 2 ตัว
threads แย่ง CPU กันแบบ spin-wait ทำให้ throughput ล่มแทนที่จะแค่ช้าลงตามสัดส่วน

**การแก้:** [`sensor.py::extract`](../source/extraction/sensor.py) จำ affinity ตอนเข้า แล้วคืนให้หลังโฟลว์แรก
ไม่ใช่การแย่ง CPU เพิ่ม — `taskset`, cgroup และ container limit ยังมีผลเหมือนเดิม
เพราะสิ่งที่คืนคือ mask ที่ผู้เรียกให้มาตั้งแต่แรก

มีเทสต์ตรึงไว้แล้วที่ `tests/test_extraction.py::test_extract_restores_cpu_affinity`

> บั๊กนี้จะไม่มีวันถูกพบถ้าไม่ได้ทำ benchmark — เป็นเหตุผลว่าทำไมแทร็กนี้ถึงคุ้มค่าที่จะทำ

## วิธีรันซ้ำ
