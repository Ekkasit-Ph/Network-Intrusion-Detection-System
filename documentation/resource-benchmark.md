## สี่ข้อสรุป

### 1. คอขวดอยู่ที่การสกัดโฟลว์ ไม่ใช่โมเดล — ห่างกัน 240 เท่า

```
สกัดโฟลว์ (NFStream + nDPI)    8,796 flow/s   ← คอขวด
เตรียมข้อมูล                  20,385 flow/s
ให้คะแนน (autoencoder)     2,131,340 flow/s
```

การเร่งโมเดลให้เร็วขึ้นไม่มีประโยชน์เลย ระบบจะยังติดอยู่ที่ 8,796 flow/s อยู่ดี
**ถ้าจะปรับปรุงสมรรถนะในอนาคต ต้องไปที่โมดูล 1** เช่นเพิ่ม `n_meters` ของ NFStreamer

### 2. GPU ทำให้ latency ต่อโฟลว์ **แย่ลง** 2 เท่า

| | CPU | GPU |
|---|---|---|
| ให้คะแนน 1 โฟลว์ | **0.067 ms** | 0.136 ms |
| ให้คะแนนเป็นชุด | 2.1M/s | 5.0M/s |
| RAM โมเดล | **3.1 MB** | 90.8 MB |

โมเดลมีแค่ 28,526 พารามิเตอร์ (115 KB) **ต้นทุนการส่งข้อมูลไป-กลับ GPU สูงกว่าการคำนวณเอง**
GPU ชนะเฉพาะตอนประมวลผลเป็นชุดใหญ่ ซึ่งไม่ใช่รูปแบบการใช้งานจริงของ IDS ที่โฟลว์ทยอยเข้ามาทีละตัว

→ **ยืนยันว่าการที่ `Dockerfile` เลือก PyTorch แบบ CPU-only เป็นการตัดสินใจที่ถูก** ไม่ใช่ข้อจำกัด

### 3. 1 core ก็พอสำหรับเครือข่ายขนาดเล็ก-กลาง

บีบเหลือ core เดียวยังสกัดได้ 4,460 flow/s และให้คะแนนได้ 1.34 ล้าน flow/s
ใช้ RAM สำหรับโมเดลแค่ 3 MB

**สิ่งที่เคลมได้:** "ทำงานได้ที่ 4,460 flow/s บน i5-11320H 1 core"
**สิ่งที่เคลมไม่ได้:** "ทำงานบน Raspberry Pi ได้" — ยังไม่ได้ทดสอบ อย่าคาดคะเนข้ามฮาร์ดแวร์

### 4. SHAP 8.7 ms ตรงตามข้อจำกัดที่ตั้งไว้

`PROJECT.md` กำหนดว่า SHAP ต้องเป็น on-demand ห้ามรันทุกโฟลว์ ตัวเลขยืนยันว่าถูกต้อง:

```
ให้คะแนน 1 โฟลว์   0.067 ms
SHAP 1 โฟลว์       8.716 ms   ← ช้ากว่า 130 เท่า
```

ถ้ารัน SHAP ทุกโฟลว์ ระบบจะรองรับได้แค่ ~115 flow/s แทนที่จะเป็น 8,796

## บั๊กที่เจอระหว่างทำ benchmark นี้

**`nfstream` หด CPU affinity ของ process จาก 8 เหลือ 2 อย่างถาวร และไม่คืนให้**
([`nfstream/utils.py::set_affinity`](../.venv/lib/python3.12/site-packages/nfstream/utils.py) เรียกจาก `streamer.py:536`)

meter ของ nfstream รันใน process แยกอยู่แล้ว การบีบนี้จึงไปโดนแต่**ทุกอย่างที่อยู่ถัดจากตัวสกัด**
— การ scale, การให้คะแนน, SHAP — ซึ่งใน [`live_capture.py`](../web/backend/live_capture.py) อยู่ใน process เดียวกันทั้งหมด

**ผลกระทบที่วัดได้:**

| | ก่อนแก้ | หลังแก้ |
|---|---|---|
| ให้คะแนนเป็นชุด | 10,220 flow/s | **2,275,190 flow/s** (222 เท่า) |
| SHAP | 90.1 ms | **9.4 ms** (10 เท่า) |

สาเหตุที่รุนแรงขนาดนี้: torch ตั้ง thread pool ไว้ 4 threads แต่เหลือ CPU แค่ 2 ตัว
threads แย่ง CPU กันแบบ spin-wait ทำให้ throughput ล่มแทนที่จะแค่ช้าลงตามสัดส่วน

**การแก้:** [`sensor.py::extract`](../source/extraction/sensor.py) จำ affinity ตอนเข้า แล้วคืนให้หลังโฟลว์แรก
ไม่ใช่การแย่ง CPU เพิ่ม — `taskset`, cgroup และ container limit ยังมีผลเหมือนเดิม
เพราะสิ่งที่คืนคือ mask ที่ผู้เรียกให้มาตั้งแต่แรก

มีเทสต์ตรึงไว้แล้วที่ `tests/test_extraction.py::test_extract_restores_cpu_affinity`

> บั๊กนี้จะไม่มีวันถูกพบถ้าไม่ได้ทำ benchmark — เป็นเหตุผลว่าทำไมแทร็กนี้ถึงคุ้มค่าที่จะทำ

# ภาค 2 — บีบสเปกลงให้ใกล้บอร์ดเล็ก

`python -m scripts.benchmark --constrained --quotas 25,50,100,200,400 --memory-max 2G --isa default`
ผลดิบ: [`artifacts/benchmark-constrained.json`](../artifacts/benchmark-constrained.json)

## บีบอะไรได้ บีบอะไรไม่ได้

| | วิธี | สถานะ |
|---|---|---|
| จำนวน CPU | `CPUQuota` ของ cgroup v2 | ✅ บีบได้ต่อเนื่อง 25–400% |
| หน่วยความจำ | `MemoryMax` + `MemorySwapMax=0` | ✅ บีบได้ |
| ชุดคำสั่ง SIMD | `ATEN_CPU_CAPABILITY=default` (ปิด AVX) | ✅ บีบได้ |
| **แบนด์วิดท์หน่วยความจำ** | — | ❌ i5 ~40 GB/s · Pi 4 ~6 GB/s |
| **แคช** | — | ❌ i5 มี L3 8 MB · Pi 4 มี L2 1 MB ไม่มี L3 |
| **สถาปัตยกรรม** | — | ❌ x86-64 vs ARM64 |

> **ตัวเลขข้างล่างคือ x86 ที่ถูกบีบ ไม่ใช่การทำนายผลบนบอร์ดจริง**
> ห้ามเขียนในเล่มว่า "ทำงานบน Raspberry Pi ได้" จนกว่าจะทดสอบบนบอร์ดจริง

`CPUQuota=100%` = ได้เวลา CPU เท่ากับ 1 คอร์เต็มต่อ 1 วินาทีจริง
(ไม่เท่ากับ "1 คอร์ของ Pi" เพราะคอร์ i5 เร็วกว่าคอร์ Cortex-A72 ราว 2–3 เท่า)

## ผล (ปิด AVX ทุกแถว)

| งบ CPU | สกัดโฟลว์ | เตรียมข้อมูล | ให้คะแนน (batch) | ให้คะแนน 1 โฟลว์ p50 | SHAP p50 | RAM โมเดล |
|---|---|---|---|---|---|---|
| 25% | 289/s | 2,459/s | 105,053/s | 0.067 ms | 114.3 ms | 2.9 MB |
| 50% | 623/s | 9,095/s | 670,316/s | 0.066 ms | 27.8 ms | 2.9 MB |
| **100%** | **1,829/s** | **20,486/s** | **999,298/s** | **0.071 ms** | **17.6 ms** | **2.9 MB** |
| 200% | 5,145/s | 19,792/s | 1,494,123/s | 0.068 ms | 14.8 ms | 2.9 MB |
| 400% | 7,886/s | 20,311/s | 1,602,623/s | 0.066 ms | 10.3 ms | 2.9 MB |

### สามข้อสังเกต

**1. การสกัดโฟลว์ขยายตามงบ CPU เกือบเป็นเส้นตรง** 289 → 7,886 เมื่องบเพิ่ม 16 เท่า
ยืนยันอีกครั้งว่าเป็นคอขวดจริงและติด CPU ไม่ใช่ติด I/O

**2. latency ต่อโฟลว์ไม่ขยับเลย** — 0.066–0.071 ms ทุกระดับงบ แม้ที่ 25%
เพราะงานของโฟลว์เดียวเล็กเกินกว่าจะวัดผลจากจำนวน CPU
**ต่อให้ลดสเปกลง 16 เท่า การให้คะแนนรายโฟลว์ก็ยังเร็วเท่าเดิม**

**3. การเตรียมข้อมูลอิ่มตัวที่ ~20,000/s ตั้งแต่ 100%** เพราะเป็น Python เธรดเดียว
ให้ CPU เพิ่มไปก็ไม่ช่วย

## เพดานล่างของหน่วยความจำ

ทดสอบเส้นทางเต็ม (โหลดโมเดล + สร้าง SHAP explainer + อธิบาย 1 โฟลว์) ที่ `MemorySwapMax=0`:

| MemoryMax | ผล |
|---|---|
| 700 MB | ✅ ผ่าน |
| **600 MB** | ✅ **ผ่าน — เพดานล่าง** |
| 500 MB | ❌ ถูก OOM kill |

> ⚠️ **ตัวเลขนี้วัดที่ `nsamples=100`** ซึ่งเป็นค่าที่ deploy อยู่ตอนวัด
> ภายหลัง [explanation-quality.md](explanation-quality.md) พบว่า 100 ให้คำอธิบายที่ไม่เสถียร
> และปรับเป็น 2,000 **เพดานล่างจึงขยับเป็น 1,000 MB** ต้องอ้างตัวเลขนี้ในเล่ม ไม่ใช่ 600 MB

แยกตามชนิดหน่วยความจำ: anonymous 538 MB (จองจริง) + file-backed 339 MB (คืนได้ ส่วนใหญ่คือไฟล์ `.so` ของ torch)

| บอร์ด | RAM | พอไหม |
|---|---|---|
| Raspberry Pi 4 / 5 (4–8 GB) | 4–8 GB | ✅ สบาย |
| Raspberry Pi 4 (2 GB) | 2 GB | ✅ พอ |
| Raspberry Pi 3B+ | 1 GB | ✅ พอแบบตึง ๆ |
| Pi Zero 2 W | 512 MB | ❌ ไม่พอ |

> ยังเป็นการประเมินจากความต้องการหน่วยความจำเท่านั้น ไม่ได้รวมว่า ARM จะช้ากว่าแค่ไหน

## บั๊กที่สอง: ShapExplainer ใช้ RAM 2 GB เพื่อเก็บข้อมูล 18 KB

ตอนบีบ RAM ลง 1 GB ระบบถูก OOM kill ทันที ไล่ดูพบว่า
[`ShapExplainer.__init__`](../source/explain/shap_explainer.py) อ่าน `train.parquet`
**ทั้ง 4,269,628 แถว × 48 คอลัมน์เข้า pandas เพื่อสุ่มมาเก็บแค่ 100 แถว**

```
โหลด train.parquet ทั้งไฟล์   +2,054 MB
เก็บไว้จริง                        18 KB
```

และตัวจัดสรรหน่วยความจำไม่คืนให้ระบบ process จึงแบกค่านี้ไปตลอดอายุการทำงาน

**แก้เป็น reservoir sampling** อ่านทีละ batch 16,384 แถว สุ่มแบบสตรีม
ได้ตัวอย่างจากประชากรเดียวกันเป๊ะ (ทุกแถว benign มีโอกาสถูกเลือกเท่ากัน) แต่ใช้หน่วยความจำจำกัด

| | ก่อน | หลัง |
|---|---|---|
| สร้าง explainer | +2,054 MB | **+201 MB** |
| serving footprint รวม | 2,611 MB | **932 MB** |
| เพดานล่าง RAM | เกิน 1 GB | **600 MB** |
| additivity residual | 0.000000 | **0.000000** (ไม่เปลี่ยน) |

**พิสูจน์ว่าสุ่มถูกต้องทางสถิติ** — ทดลอง 1,500 ครั้ง เลือก 20 จาก 200 แถว:
chi-square 192.3 (df=199, ช่วงปกติ 199±20) · sd จริง 19.6 เทียบทฤษฎี 19.0
ตรึงไว้ที่ `tests/test_explain.py::test_background_sample_is_uniform_over_benign_rows`

> ⚠️ แถวที่ถูกเลือกด้วย seed เดิมจะไม่ใช่แถวเดิม → `base_value` ขยับเล็กน้อย
> เป็นการสุ่มคนละครั้งจากประชากรเดียวกัน ไม่ใช่การเปลี่ยนนิยามของ background
