## 🎬 ตอนนำเสนอ

### ช่วง 1 — เปิดเรื่อง (พูด ยังไม่ต้องรันอะไร)
> "หลังกลางภาค ผมเอาระบบไปทดสอบบนเครือข่ายจริง สร้างด้วย Mininet — มีสวิตช์ OpenFlow
> ควบคุมด้วย Ryu ทำหน้าที่ firewall จริง ๆ, มีอุปกรณ์ IoT, เซิร์ฟเวอร์, และเครื่องโจมตี
> โดยตัวตรวจจับ (NIDS) ต่อผ่าน mirror port แบบ passive — ดูทราฟฟิกได้แต่บล็อกอะไรไม่ได้เลย"

*(ชี้แผนภาพ topology ถ้ามีสไลด์)*

### ช่วง 2 — รันเดโมสด (พิมพ์คำสั่งใน terminal ที่ ssh ไว้)
```bash
sudo bash ~/nids/network_simulation/demo/run_live_demo.sh 180
```
> "คำสั่งนี้จะเปิดเครือข่ายจำลอง ปล่อยทราฟฟิกปกติหลายแบบ — เว็บ, DNS, SSH, การรับส่งไฟล์
> แล้วช่วงท้ายจะจำลองการโจมตี 3 แบบ"

**สลับไปหน้าเบราว์เซอร์** (แดชบอร์ด) ระหว่างที่มันรัน:
> "ตรงนี้คือ flow ที่ไหลเข้ามาแบบเรียลไทม์ ช่วงแรกเป็นทราฟฟิกปกติ โมเดลไม่แจ้งเตือน —
> อยู่ในงบ false positive ที่เราตั้งไว้ไม่เกิน 5%"

*(รอ ~2 นาที จนถึงช่วงโจมตี — หน้าจอจะเริ่มขึ้นแดง)*
> "ตอนนี้เครื่องโจมตีเริ่มทำงาน — จะเห็นแถวแดงเด้งขึ้นมาเยอะ ๆ นี่คือ port scan,
> SYN flood, และ SSH brute-force ที่โมเดลจับได้"

### ช่วง 3 — โชว์ SHAP (คลิกที่ flow แดงสักอัน)
> "พอคลิกที่ flow ที่ถูกจับ ระบบอธิบายได้ว่า**เพราะฟีเจอร์อะไร** — อันนี้คือ SHAP
> เห็นไหมว่าตัวขับหลักคือ 'จำนวนพอร์ตปลายทางที่ต่างกัน' ซึ่งตรงกับพฤติกรรมสแกนพอดี
> ระบบไม่ใช่กล่องดำ — บอกเหตุผลได้"

*(ถ้าหน้าแรกไม่เห็นแดง: ติ๊ก checkbox "Anomalies only" หรือเข้าแท็บ Incidents)*

### ช่วง 4 — เรื่อง domain shift (สลับไปสไลด์ตัวเลข)
> "แต่กว่าจะมาถึงจุดนี้ไม่ง่าย ตอนแรกที่เอาโมเดลที่เทรนด้วยชุดข้อมูล NF-ToN-IoT-v2
> มารันบน Mininet — **มันจัดลำดับกลับด้านสมบูรณ์ AUROC เท่ากับ 0**
> คือทราฟฟิกปกติกลับได้คะแนนผิดปกติสูงกว่าการโจมตีอีก"

> "ผมไล่หาสาเหตุ: autoencoder วัดแค่ว่า 'ห่างจากค่าเฉลี่ยที่เคยเห็นแค่ไหน' แต่ไม่รู้ทิศทาง
> พอเครือข่ายใหม่มีนิยาม 'ปกติ' ต่างจากชุดฝึก ความสัมพันธ์เลยพลิก
> **ทางแก้คือเทรนใหม่ด้วยทราฟฟิกของเครือข่ายนั้นเอง → AUROC กลับมาเป็น 0.994**
> ซึ่งพิสูจน์ว่าปัญหาคือความต่างของข้อมูล ไม่ใช่ข้อจำกัดของวิธีการ"

### ช่วง 5 — finding brute-force (ปิดให้ดูเป็นผู้ใหญ่)
> "อีกข้อค้นพบ: ไม่ใช่ทุกการโจมตีจับง่ายเท่ากัน scan กับ flood แยกออกชัดมาก
> แต่ SSH brute-force หน้าตาที่ระดับ flow **แทบเหมือน SSH ปกติ** — เพราะมันคือ SSH ที่ล็อกอินไม่ผ่าน
> การจะจับมันให้ครบต้องยอมให้ false positive เกิน 5% ซึ่งเราไม่ยอม
> ข้อสรุปคือการโจมตีแบบนี้ต้องอาศัยการ**รวมกลุ่มเชิงพฤติกรรม** (นับความถี่จากต้นทางเดียว)
> ซึ่งเป็นหน้าที่ของโมดูลรวมการแจ้งเตือนที่เราทำไว้ — ระบบเลยต้องมีทั้งสองชั้น"

### ช่วง 6 — สรุป
> "สรุปหลังกลางภาค: (1) ประเมินครบทุกด้าน (2) เพิ่มโมดูลรวมการแจ้งเตือน
> (3) ทดสอบบนเครือข่ายจริง เจอและแก้ปัญหา domain shift ได้ (4) ทำเครือข่ายจำลองให้สมจริง
> หลายโปรโตคอลหลายการโจมตี พร้อมข้อค้นพบเรื่องขอบเขตของการตรวจจับ"

## ❓ คำถามที่อาจโดนถาม (เตรียมคำตอบสั้น)

**Q: ทราฟฟิกจำลองนี่จริงแค่ไหน?**
> แพ็กเก็ตเป็นของจริง (Linux TCP/IP stack + OVS จริง) โปรโตคอลจริง (DNS/SSH ผ่าน nDPI)
> ที่จำลองคือเนื้อหาและขนาดเครือข่ายที่เล็กกว่าจริง

**Q: firewall (Ryu) เป็น firewall จริงไหม?**
> จริง — policy ถูกแปลงเป็นกฎ OpenFlow ติดตั้งบนสวิตช์ OVS แล้วบังคับใช้ระดับ kernel
> ทดสอบแล้ว telnet/RDP ถูกดรอปจริง (นับ packet ที่กฎ drop ได้), web ผ่าน

**Q: ตัวเลข AUROC 0.994 เทียบกับ 87% บนชุดข้อมูลจริงได้ไหม?**
> เทียบไม่ได้ คนละเงื่อนไข — ตัวเลขจาก Mininet เป็นการทดสอบ integration + ทิศทาง
> ไม่ใช่การวัดสมรรถนะสัมบูรณ์ (ทราฟฟิกสังเคราะห์ทั้งหมด)

**Q: FPR ในเดโมเกิน 5% นิดหน่อย?**
> ใช่ เพราะยอมกดเกณฑ์ลงเพื่อจับ brute-force — เป็น tradeoff ที่อธิบายไว้ใน finding
> ถ้ายึด 5% เคร่งครัดจะจับ brute-force ได้น้อยลง ซึ่งเป็นเรื่องที่ชั้นรวมกลุ่มมารับช่วง

## 🔧 ถ้าเดโมพัง หน้างาน (recovery)
- **แดชบอร์ดว่างเปล่า / flows=0** → เครือข่ายไม่ forward: `sudo mn -c` แล้วรัน `run_live_demo.sh` ใหม่ (สคริปต์เริ่ม Ryu ให้เอง)
- **เข้าเว็บไม่ได้** → เช็ค `sudo systemctl is-active nids-backend` บน VM; ถ้าตายให้รันคำสั่ง backend ในหัวข้อเตรียมตัวใหม่
- **ทุกอย่างพัง** → เปิดวิดีโอ backup
